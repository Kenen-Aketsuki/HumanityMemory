## §0 一屏速览

**要解决的问题**

1. **死板**：四类 kind 是硬分类，判据写在 prompt 里靠模型当场自觉执行；梯子、TTL、压缩门槛全是静态常量，判错了没有反馈回路。
2. **烧 token**：每天复盘把当天全部日志 **加全部存量条目** 塞进上下文让模型比对、分类、逐条复核。存量越大越贵，且判据是自然语言问句，成本最高的"判断"交给了最不可复现的执行者。

**一句话结论**

> 记忆只分 **经历** 与 **经验** 两类。每条记忆带三个机器可算的维度——  
> **活跃度**（周期内被检索的加权次数）、**可信度**（是否需要在被读到前先验一下）、**遗忘等级**（决定多久裁定一次、以及经历压缩多深）。  
> 模型每天只做三件事：总结条目、给初始可信度与重要性、报告使用证据分级。  
> **升降、加分、遗忘、查重全部由工具按阈值计算，不经过模型。**  
> **所有阈值与等级档位来自 TOML 配置文件，代码里不写字面量。**

**收益来源**（省 token 的两个真来源，不是"少写几条"）

| 环节   | 旧                        | 新                             |
| ---- | ------------------------ | ----------------------------- |
| 查重   | 存量全量进上下文，模型逐条比对          | 向量检索 top-3，只把候选短文本给模型         |
| 复核   | 到期项逐条 `matched`，每天一笔固定开销 | **零**——裁定是 SQL 比较阈值，不进 prompt |
| 库龄影响 | 存量越大越贵（线性）               | 基本恒定                          |

**最关键的转变**：验证成本从「条目数 × 时间」变成「被真正使用的次数」。  
没人用的条目，一分钱不花；可信度高的条目，永远不主动验。

**别走回头路**（最容易重犯的五条）

1. 别为经历保留"可信度演进"——经历是叙事，不谈真假，它的可信度就是遗忘等级的派生值。
2. 别让活跃度纯累计不清零——那会富者愈富、老条目永不遗忘。
3. 别用"日志没提到"当反证——流程使用是稀疏的，**沉默什么都不是**。
4. 别让模型决定分值——模型只报"真/假"和"证据级别"，分值是工具按公式算的。
5. 别在代码里写死等级档位或阈值——等级是**数据**，加一档只改 TOML。

## §1 两类记忆

|      | **经历**                          | **经验**                                                  |
| ---- | ------------------------------- | ------------------------------------------------------- |
| 是什么  | 发生过的事，一条一个单一事务                  | 可复用的判定与结论，统合旧的 knowledge / state / case                 |
| 时间戳  | **必须有**，与内容分列存储                 | 一般不需要                                                   |
| 例子   | 「今天吃饭」「今天洗澡」「Bug #10805 引导不指餐厅」 | 「`ResolveTask` 末尾 `UsesScene(taskId,null)==true` 会短路兜底」 |
| 会压缩吗 | **会**，等级越低压得越狠                  | 记录后不再压缩                                                 |
| 可信度  | 遗忘等级的派生值（等级低 → 可信度低）            | 独立演进，双通道升降                                              |
| 遗忘速度 | 快（周期约经验的 1/2）                   | 慢                                                       |
| 写入方式 | 直接新建；压缩时**覆盖原条**                | 先语义查重；覆盖时记失效链                                           |

### 怎么判一条内容进哪类

**唯一判据：它是否需要回答「什么时候发生的」。**

- 需要 → 经历。哪怕结论很硬（「Bug #10805 的根因是 StockBread 三条静默出口」），它绑死在一个事件上，是经历。
- 不需要 → 经验。哪怕它昨天才成立、下周就变（「项目用 HybridCLR」），它谈的是"现在是怎么回事"，是经验。

> 旧的 `kind=state` 与 `kind=knowledge` 的差别，在新方案里**不再靠分类区分，而靠可信度区分**。  
> 一条易变的现状，初始可信度给低（0.3），因此每次被读到都会被要求先验一下，很快就能发现它变了；  
> 一条稳定的机制，初始可信度给高一点，几次验证后就免检。  
> **这是本方案相对旧方案最本质的简化：用连续的分数替代离散的类别，把"这属于哪类"这个最主观的问题消掉了。**

### 经历的一条 = 一个单一事务

「今天吃饭、洗澡」是**两条**，不是「今天做了一些事」一条。拆分原则：

- 能用一个动词短语单独命名的，就是一条。
- 拆分过细不是问题——低等级会快速压缩；拆得过粗才是问题，它会让一个重要事件被一堆琐事稀释。
- 同一件事被写成两条，属于录入阶段的去重问题，**不靠压缩阶段合并来补救**（见 §3.3）。

## §2 三个评分维度

### 2.1 活跃度 · 纯机器

**定义**：本检查周期内，该条目被检索命中时的**相关性加权累加值**。

```
单次贡献 = max(0, sim - sim_floor) ^ curve_power      # sim_floor ≈ 0.35, curve_power = 2
activity += 单次贡献
```

用平方而非线性：高相关的一次命中，价值远大于擦边命中的十次——否则"什么都能蹭一点"的条目会靠数量取胜。

**周期末清零**（这是本方案的关键简化）：遗忘等级裁定完毕，`activity = 0`，`period_start = now`，倒计时按**新等级**的周期重新起算。

> 为什么不用滑动窗口：滑动窗口要按天分桶或存时间序列，实现和查询都重。  
> 清零制只需 `activity: float` + `period_start: int` 两个字段，一条 `UPDATE` 完成，  
> 且天然实现"每个周期独立评估"，不存在历史惰性。

### 2.2 可信度 · AI 定初值，工具按证据调分

**取值范围** 0~1。两条腿，分开记：

| 通道           | 触发              | 效果          |
| ------------ | --------------- | ----------- |
| `verify`     | 有人主动核对了现实，结论为真  | 按**间隔**加分   |
| `contradict` | 日志/上下文出现与之矛盾的内容 | 按同一条幂律降分，系数换成 `loss_k`（更狠） |

#### 加分公式：间隔本身就是证据

> 隔了半年再看一眼它还是对的，这比昨天刚验过今天又验一次，信息量大得多。  
> **时间跨度是对稳定性的证明。**

```
delta = min(1 - confidence, gain_k * interval_days ^ gain_alpha)
gain_k = 0.05, gain_alpha = 1.4      # 出厂值，可在 TOML 调
```

| 距上次验证 | 加分    | 可信度（从 0.3 起） |
| ----- | ----- | ------------ |
| 1 天   | +0.05 | 0.35         |
| 3 天   | +0.23 | 0.53         |
| 7 天   | +0.70 | **1.00**     |

**证伪更狠**：`delta = -min(confidence, loss_k * days ^ gain_alpha)`，`loss_k = 0.15`（约为证实的三倍）。  
理由：证实是"还没被推翻"，证伪是"已经错了"——信息量不对等。

> **口径说明（2026-11-16 实施时定）**：上表原写 `contradict`「直接降分，不受间隔加成」，
> 与下面这条公式冲突（公式里带着 `days ^ gain_alpha`）。按公式与 TODO 5 的「对称扣减」实现：
> 证伪走**同一条幂律**，只把系数换成 `loss_k`。理由是「错了多久才发现」同样是信息 ——
> 一条错了半年的结论，比一条昨天刚写成今天就错了的，更该被打下去。

#### 两个阈值，不是一个

| 阈值               | 出厂值  | 行为                                      |
| ---------------- | ---- | --------------------------------------- |
| `verify_on_read` | 0.5  | 低于此值，被检索命中时返回带 `needs_verify` 标记，提示先核一下 |
| `treat_as_fact`  | 0.85 | 高于此值，视为事实，**不再主动复核**，返回时不带任何提示          |

中间带（0.5~0.85）：可正常使用，不强制验证，也不给"已定论"的背书。

**⚠️ 满分只豁免"例行复核"，不豁免"主动推翻"。** 任何时刻日志或上下文出现矛盾，`contradict` 通道照常把它打回去。这条是防"易变事实被熬成永久真理"的唯一保险，不能省。

#### 不可验型经验走日志通道

流程性/偏好性经验（「引导卡住先看三处静默出口」）没有可对照的现实，验不了。  
它们靠**日志里出现的使用痕迹**加分，证据必须分级：

| 级别     | 判据                              | 计分权重  |
| ------ | ------------------------------- | ----- |
| **L1** | 可观测动作、工具调用记录、明确的执行痕迹            | 1.0   |
| **L2** | 复盘模型判定当日确实执行了该流程                | 0.5   |
| **L3** | 仅文本共现（「忘了跑 `memory_stats`」这种提到） | **0** |

**硬规矩：某个流程今天没出现在日志里，不能视为它没被使用，绝不据此扣分。**

#### 经历的"可信度"是派生值

经历不谈真假，只谈"记得清不清楚"。所以不单独演进、不需要 AI 打分：

```
confidence = 0.2 + 0.8 * (forget_level / 最高等级)   # 0 级 = 0.2，顶档 = 1.0
```

按最高等级归一，而不是写死 `0.16 * level`：后者在 5 档下恰好封顶 1.0，
档数一扩到 10 就会算出 1.8。归一后 5 档时的取值与原式完全一致（1 级 0.36 / 3 级 0.68 / 5 级 1.0）。

它只用于展示和排序，**不驱动任何验证行为**。

### 2.3 遗忘等级 · 纯机器、可配置扩展

**当前分 0~10 级**，10 最高（最难忘），0 是遗忘层。**等级档位是数据，不是枚举**——加一档只需在 TOML 的 `[[forget.levels]]` 里加一段（见 §6）。

表分两段，这是整套阶梯的核心取舍：

- **1~5 级是短时记忆**：两种周期都在 1 周以内，一天到一周就裁定一次。
  新条目在这里快速试错 —— 被检索到就往上爬，没人再问就往下掉。
- **6~10 级是长期记忆**：从月级起步，逐级拉长到一年半。
  只有连续多个周期都保持活跃的条目才配待在这一段。

所以「升到 6 级」是一条真正的分水岭：那之前是工作记忆，那之后是沉淀。

| 等级     | 检查周期（经验 / 经历） | 升级阈值 | 降级阈值 | 经历压缩 |
| ------ | ------------- | ---- | ---- | ---- |
| **10** | 540 / 365 天   | —（顶档） | < 27.2 | 完整 |
| **9**  | 365 / 240 天   | ≥ 34 | < 20   | 完整 |
| **8**  | 240 / 120 天   | ≥ 25 | < 14.4 | 完整 |
| **7**  | 120 / 60 天    | ≥ 18 | < 10.4 | 完整 |
| **6**  | 30 / 21 天     | ≥ 13 | < 7.6  | 完整 |
| **5**  | 7 / 7 天       | ≥ 9.5 | < 5.6 | 完整 |
| **4**  | 5 / 5 天       | ≥ 7  | < 4.0  | 完整 |
| **3**  | 3 / 3 天       | ≥ 5  | < 2.8  | 一句话 |
| **2**  | 2 / 2 天       | ≥ 3.5 | < 1.6 | 一句话 |
| **1**  | 1 / 1 天       | ≥ 2  | < 0.5  | 一句话 |
| **0**  | 不参与周期裁定    | 复活 ≥ 2 次深度命中 | —（只能删除） | 标题级 |

**滞回缓冲**：升级阈值恒大于本档降级阈值、也大于上一档的降级阈值（2>0.5、3.5>1.6、5>2.8、7>4、9.5>5.6、13>7.6、18>10.4、25>14.4、34>20），中间是死区。活跃度落在死区时**不动作**，避免边界每天抖动升降。

**裁定规则**（周期末执行，纯 SQL）：

1. `now - period_start >= 当前等级周期` → 该裁定了。
2. `activity >= 升级阈值` → 等级 +1（**最多升一级**，不跳级）。
3. `activity < 降级阈值` → 等级 -1（**最多降一级**）。
4. 否则维持原级。
5. 无论升、降、维持，**都清零活跃度并把周期起点重置到 now**，倒计时按新等级重算。

> 不跳级是有意的：升要连续多个周期达标，才配得上更高的位置；  
> 降也要连续冷落，避免"一个冷清的季度"就把一条重要经验直接打到遗忘层。

#### 初始等级：3~5，长期段不可设

**新条目一律落在 3、4、5 三档之一**，具体由 AI 给出的 `importance` 决定。
三档全部位于短时记忆段（周期 3~7 天）：

| importance | 初始等级  | 说明                          |
| ---------- | ----- | --------------------------- |
| ≥ 0.55     | **5** | 被用户明确批评、重大失误、关键架构决策、长时间疑难排查 |
| 0.30~0.55  | **4** | 默认落点                        |
| < 0.30     | **3** | 琐事：吃饭、洗澡、改个 typo。天生短命       |

**6 级及以上不可由录入直接设定**，只能靠连续多个周期的真实活跃度升上去。

> 这条是本方案的一个原则：**长期记忆是挣来的，不是写上去的**。  
> 如果开局就能落 6 级，等级就退化成"AI 觉得这事重要"的主观标签——而主观判断正是本方案要消掉的东西。  
> 现实收益也很直接：一条开局被高估的"重要经验"，如果其实没用，几个周期后会自己降下来；  
> 而开局能直接落长期段的话，它会在高位赖很久。

> **为什么不是"开局落 4 级、30 天不管也不掉"**：那正是旧表的行为，也是被废掉的原因 ——  
> 一条开局被高估的经验要在 180 天后才有第一次裁定，短时记忆根本没有轮转的机会。  
> 现在所有新条目都先当工作记忆：一周内被检索到就升，没人问就掉。  
> 代价是低频高价值内容要靠 `importance` 与后续检索给自己挣位置，而不是靠开局定终身。

> **扩展档位时**：上限由 `[[initial.bands]]` 自己声明，校验只要求「不超过最高等级 - 1」
> 且「不低于 2」。加档不会自动抬高录入上限 —— 想放宽得显式改 bands，这是有意的：
> 新档位该不该开放给录入，是一个需要人判断的语义决定，不该被"扩表"顺手带出来。

### 2.4 为什么初始等级要分档

若所有条目都从同一档起步，**纯活跃度驱动会杀掉"低频高价值"内容**——  
「那次排查了三天才找到的根因」如果一个月内没人再问起，活跃度 0 → 降级 → 压缩 → 半年后只剩标题。

所以 `importance` 决定初始落点，让两类内容各走各的通道：琐事三个周期自然消失，重要事件开局就在 5 级（7 天）。

## §3 遗忘、复活与压缩

### 3.1 遗忘 = 归档，不是删除

降到 0 级 = 进入**遗忘层**：

- 不参与常规检索（和归档同义）
- 正文一个字不动
- 可以被人主动"深度回忆"捞回来

**0 级仍保留完整正文**，因为遗忘判定是纯机器算的，纯机器不该有不可逆的破坏力。

### 3.2 深度回忆与复活

```
常规检索 → top-N 最高相似度 < deep_recall_floor(0.35) → 视为检索失败 → 触发深度回忆
深度回忆 → 只在 0 级层内检索 → 命中即返回，且标记「这是已遗忘的记忆」
```

| 事件                                              | 结果                                     |
| ----------------------------------------------- | -------------------------------------- |
| 0 级条目被深度回忆命中 **1 次**                            | 记 `revive_hits = 1`，仍在 0 级             |
| 累计命中 **≥ revive_hits（默认 2）**                    | **复活到 1 级**，`period_start = now`，活跃度清零 |
| 0 级停留超过 `level0_purge_days` 且 `revive_hits` 未达标 | 进删除候选（只报告），显式确认后物理删         |

**复活回 1 级，不回 3 级**——"快速回忆快速死亡"。  
想起一次不代表记住了，它必须连续证明自己：回到濒死位，下个周期还得再有足够活跃度，否则立刻再死一次。  
回 3 级等于给了一次免费续命，会让遗忘层变成回收站。

**这条复活链只覆盖经历**：`revive_hits` 列只有 `episodes` 有（见 §7.1 的字段分配），
所以经验落到 0 级时能被深度回忆捞出来看，但不会自动复活 —— 它走 `level0_purge_days`
进删除候选，或人工恢复。这是 schema 的既有不对称，不是实现漏了；经验半衰期 10 年，
实际几乎掉不进遗忘层，为它加一列要动全部库，不划算。

### 3.3 经历的压缩

**只有经历压缩，经验永不压缩**（压缩会丢失精确性，而经验的价值就在精确）。

**压缩是内容压缩，不是条目合并。** 500 字的记录压成 100 字，条目数不变、`id` 不变、`at` 不变。  
同一件事被写成两条，是**录入阶段**的问题（靠 §1 的拆分原则把关），不留给压缩阶段去合并——  
压缩阶段合并是拿不可逆的覆盖去修补一个本该当场堵住的漏洞。

压缩按等级分档，`compression_level` 越大压得越狠（沿用现有字段，默认 0 = 未压缩）：

| 落到等级        | 目标 `compression_level` | 压缩动作              |
| ----------- | ---------------------- | ----------------- |
| 10 ~ **3**  | 0                      | 完整，不动             |
| **2**       | 1                      | 中度压缩：去过程，留关键步骤与结论 |
| **1**       | 2                      | 压到一句话             |
| **0**       | 3                      | 标题级 + 一句摘要        |

**压缩区必须整个落在考察期之下** —— 这是 10 档表定下来后新加的一条硬约束：

1~5 级同时是「录入落点」和「晋升考察期」。记忆在这里证明自己够不够格升到长期段，
而压缩是**覆盖写 `content`**：一旦压成一句话，它升到 8 级也回不来。
如果把 3 级（录入落点之一）也放进压缩区，等于用销毁证据的方式做判断 ——
所以 3 级及以上一律不压，`required_compression` 前四位 `[3,2,1,0]`
与旧 5 档表完全一致，只是把 L3 明确排除在外。

**时间戳与内容分列存储正是为了这个**：压缩只动 `content`，`at` 永远指向事件真实发生时刻，不会漂移成压缩时刻。

#### 3.3.1 谁来做压缩：裁定入队，AI 执行

这里有一条边界必须划清：**降级判定是纯 SQL，压缩改写是生成任务**，两者不能塞进同一个事务。

所以压缩走队列，但**不需要任何"待压缩"标记字段**——需求完全可以从配置推导：

```sql
-- 待压缩队列：当前压得不够深
-- :target 由 Python 侧查表 required_compression[forget_level] 代入，SQL 不支持数组下标
SELECT id, at, content, compression_level, forget_level
  FROM episodes
 WHERE archived_at IS NULL
   AND compression_level < :target[forget_level];
```

流程：

1. 机械裁定只改 `forget_level`，**一个字节的 content 都不碰**
2. AI 下次复盘时取出队列，逐条压，压完把 `compression_level` 写到目标值
3. 压完两边相等，自动出队

队列天然自愈：不需要"已处理"标记，不需要补偿逻辑，**队列为空时这一步完全不进 prompt**。  
而且队列只装真正降过级的条目，每天的量很小——不是全量重压。

**压缩必须带 `id` 定向覆盖**，禁止"新建一条压缩版 + 归档旧条"：后者会让同一件事在库里留下多份详略版本，  
且新条目的 `at` 会漂成压缩时刻，时间线就此错乱。

审计落 `memory_events{id, from_level, to_level, before_len, after_len}`——  
压缩是有损操作，`after_len` 掉得离谱时（比如 500→8 字）得有据可查。

### 3.4 压缩的入口只有两个

| 入口     | 触发                 | 是否带 `id` |
| ------ | ------------------ | -------- |
| 队列驱动   | AI 复盘时取 §3.3.1 的队列 | 是        |
| 用户显式要求 | 指明某条重压             | 是        |

**不存在"AI 自己判断这段是对某条旧经历的压缩版，于是去覆盖它"这条路径。**  
录入永远新建，压缩永远覆盖，两条路不交叉——这样 `is_compression` 这类标记也就不需要了。

## §4 AI 的职责边界

**只做三件事，多一件都不要做。**

| # | 职责      | 产出                                   | 说明              |
| - | ------- | ------------------------------------ | --------------- |
| 1 | 从日志总结条目 | 经历 N 条 / 经验 M 条                      | 判断进哪类，见 §1      |
| 2 | 给初值     | `confidence`（经验）、`importance`（两类）    | 一次定完，之后不再由 AI 调 |
| 3 | 报使用证据   | `[{item_id, level: L1/L2/L3, note}]` | 只报级别，不算分        |

**AI 明确不做的事**（这些全部归工具）：

- ❌ 决定升降级
- ❌ 计算加多少分
- ❌ 决定某条该不该遗忘
- ❌ 判断两条是否语义重复（只判断候选，检索由向量库做）
- ❌ 逐条核对到期清单（**这个清单再也不出现**）

**为什么把算分权收归工具**：模型可以用措辞影响自己给出的分数（"这条非常重要"→ 0.95）。  
让它只回一个布尔值 + 一个证据级别，分值由公式算，杜绝这种漂移。  
代价是分值的形成过程离开了上下文，所以**必须留审计记录**（§5.4）。

**这三条边界落地在哪**：`skills/humanity-memory/references/consolidate-task.md` 的模板
（定时复盘用，只有两处 `{{占位}}` 给各仓库微调）+ `consolidate_preview` 返回的 `instructions`。
两处必须一致 —— 模板是"说明书"，`instructions` 是随数据一起送到的"现场指令",
后者权重更高。改一处不改另一处，模型会照着更权威的那份做（第 13 项就踩过这个坑）。

## §5 工具侧的机械计算

### 5.1 周期裁定（零 token）

```sql
-- 找出该裁定的条目（纯 SQL，不产生任何模型调用）
SELECT id, forget_level, activity, confidence
  FROM knowledge
 WHERE archived_at IS NULL
   AND (:now - period_start) >= :period_days[forget_level];
```

逐条按 §2.3 规则比较阈值，一次事务内完成升级/降级/清零。  
**压缩不进这个事务**——裁定只改 `forget_level`，改写由 AI 按 §3.3.1 的队列执行。

### 5.2 可信度调整（由工具算分）

```
memory_verify(item_id, ok=true|false, level="L1"|"L2"|"L3")

interval = (now - last_verified_at) / 86400      # 天；未验证过则从 created_at 起算
if ok:
    delta = min(1 - c, gain_k * interval^gain_alpha) * level_weight(level)
    c += delta
else:
    c -= min(c, loss_k * interval^gain_alpha)
c = clamp(c, 0, 1)
last_verified_at = now
```

模型只传 `ok` 与 `level`，**不传分值**。

### 5.3 录入查重（经验）

```
1. 新条目 content 做 embedding
2. 向量检索 top-k（经验层，k = dedup.topk，默认 3）
3. 最高相似度 >= dup_floor(0.90) → 放弃录入
      → 转而对该既有条目 activity += dup_bonus
      → 若新内容明显更准确/更新，走「覆盖」路径：新建 + 旧条 invalid_at
4. 否则正常录入，落初始等级（§2.3 表）
```

查重由向量库完成，模型只看 top-k 的短文本做最终确认——**不再全量比对存量**。

**实现口径**（`store._dedup_probe` + `write_experience`）：

| 情况 | 行为 | 理由 |
| --- | --- | --- |
| 相似度 ≥ 阈值 | 不新建，`activity += dup_bonus`，落一条 `dedup` 审计事件，**返回既有条目**且 `deduped=True` | 返回既有条目而不是报错：对调用方来说「我要的知识已经在库里」这个结果是成功的，不该当失败处理 |
| 候选已失效 / 已归档 | 跳过，不参与比较 | 被推翻过的结论不构成重复，新写的很可能正是它的替代品；不排除它，越像越写不进去 |
| 没有 embedding（未配服务 / 调用失败） | 跳过查重，照常写入 | 查重是优化。一旦它变成写入的前置条件，没网就等于不能用 |
| `invalidates` 非空 | **自动跳过查重** | 「我这条取代旧的」本来就该和被取代者相似。不跳过就会出现旧条被失效、新条被拦，凭空空掉一条 |
| `allow_duplicate=True` | 跳过查重，强制新建 | 措辞相似但确实是另一条结论时的逃生口 |

只有**经验**查重。经历不查：同一天做两次同样的排查，是两件事，不是一条被写了两遍。

### 5.4 审计（不能省）

每次分值和等级变动都落一条记录：

```json
{"item_id": "k_x", "at": 1763.., "kind": "verify",
 "delta": 0.23, "before": 0.30, "after": 0.53,
 "interval_days": 3, "level": "L1", "reason": "复核 ResolveTask 仍短路"}
```

存独立的 `memory_events` 表（推荐），或退而求其次写进 `meta.events` 数组。

**理由**：分值的形成过程脱离了上下文，三个月后必须能回答「这条凭什么 1.0」。  
旧方案文档里已经强调过这一点——只加计数不留结构化证据，事后无法审计。

### 5.5 检索侧排序

```
final_score = w_retrieval * sim
            + w_importance * importance
            + w_level * level_factor(forget_level)
```

`level_factor` 默认按公式算：`(level / max_level) ^ level_factor_power`（0 级恒为 0，且 0 级根本不进常规检索）。  
若想逐级手调，在 TOML 里填 `level_factor` 映射表覆盖公式。

**不加这一项会出事**：旧库实测 top-6 的相似度区间只有 0.07，噪音条目极易挤进来。  
遗忘等级是唯一能表达"这条已经不重要了"的排序信号。

**落地细节**（`store._level_of`）：日志没有 `forget_level`，第三项恒按 1.0 ——
按 0 判会把它整类打成 0 分沉底，而它本来就靠 `type_weight`（0.90）与复盘清空
体现「原始素材」的定位。旧的「强度」链（半衰期衰减 × 使用频次）已删除：
它与等级项是两套「这条有多重要」，同时存在会互相抵消。

## §6 统一配置文件

### 6.1 三条硬原则

1. **代码里不写字面量阈值，也不写"配置类"**。`config.py` 退化为纯加载器——只负责找到文件、解析、合并、校验，自身不含任何可调数值。
2. **出厂默认随包分发**（`memory.default.toml`），用户能读、能注释、能改。
3. **遗忘等级是数据不是枚举**。加一档、改周期、改阈值，只改 TOML，不碰代码。

### 6.2 为什么是 TOML


| 候选         | 判断                                                      |
| ---------- | ------------------------------------------------------- |
| **TOML** ✅ | 支持注释（这批参数必须能自解释）、支持数组表（等级列表天然是数组）、`tomllib` 为 3.11+ 标准库 |
| YAML       | 要 PyYAML（C 扩展），违背"无额外依赖"                                |
| JSON       | 标准库但**不能写注释**，配置无法自解释                                   |
| .env       | 只有扁平 KEY=VALUE，表达不了"每档等级一组参数"                           |

Python 3.10 需加一条条件依赖：`tomli>=2.0; python_version < "3.11"`（纯 Python，约 8KB，3.11+ 完全不装）。

### 6.3 文件位置与合并优先级

| 层  | 路径 | 定位 | 是否入库 |
| -- | --- | --- | ----- |
| 出厂 | 包内 `src/humanity_memory/memory.default.toml` | **全量**默认值，随代码发布，用户不该改 | ✅ 是 |
| 安装 | `<安装根>/memory.toml`（与 `.env` 同目录） | **全量模板**，`config template` 整份生成 | 否（本机） |
| 用户 | `~/.humanity-memory/memory.toml` | **增量**，跨项目偏好 | 否（本机） |
| 项目 | `<项目>/.ai_memory/memory.toml` | **增量**，单项目调参，优先级最高 | 可选 |

**合并规则**：逐键深合并，优先级 项目 > 用户 > 安装 > 出厂。任何一层只写自己关心的键即可，
缺的键从更底层补 —— 所以「安装层是全量模板、出厂升级又加了新键」不会报缺项。

**为什么安装层要单独存在**：`memory.default.toml` 在包内，冻结后埋进 `_internal/`，
用户想看一眼所有可调项就得翻包目录（打包态还看不到源码）。安装层把这份全量配置摊到
`.env` 旁边：跨版本共享、重装与回滚都不动它、也不用重新打包。

**代价要清楚**：安装层放着全量就等于**接管了所有默认值**。以后出厂调了某个默认值，
安装那份的旧值会赢 —— 想拿到新默认值得手动 merge，或者删掉那个键让它回落。
只改几项的话，用户级 / 项目级更省心。

安装根的双态解析与 `.env` 完全一致（源码态 = 仓库根；冻结态 = 发布根，即 exe 穿 junction
resolve 后的上一级），实现见 `config.install_config_file()`。

### 6.4 凭据不进 TOML

`HM_EMBED_API_KEY` 这类仍走 `.env` / 环境变量，理由：

- 有轮换、CI 注入、mcp.json env 覆盖的需求，环境变量一层现成可用
- 配置文件和密钥文件分开，`.ai_memory/memory.toml` 才敢放心入库/分享
- 避免"改个参数顺手提交了密钥"

分工一句话：**TOML 存行为，.env 存凭据。**

### 6.6 启动时校验（配置写错要早失败）

`config.py` 加载后必须做一致性检查，任一不通过就**拒绝启动并指出具体哪一段**：

| 检查                                               | 理由                                    |
| ------------------------------------------------ | ------------------------------------- |
| `levels` 中 `level` 无重复，且含 0                      | 等级是主键                                 |
| 每个非顶档都有 `up_threshold`，除 0 级外都有 `down_threshold` | 缺了会静默不动作                              |
| 相邻档 `up_threshold[i] > down_threshold[i+1]`      | **滞回缓冲不能倒挂**，否则边界抖动                   |
| `initial.bands` 的最大 `level ≤ 最高等级 - 1`           | 顶档不可设                                 |
| `initial.bands` 的最小 `level ≥ 2`                  | 下限                                    |
| `0 < verify_on_read < treat_as_fact < 1`         | 中间带必须存在                               |
| `revive_to_level` 必须是存在的等级                       | 复活目标要落地                               |
| `required_compression` 长度 = 等级档数                 | 数组按 `forget_level` 下标取值，短了会越界、长了会静默错位 |

## §7 存储改动（对照现有 schema）

**一句话结论：v4 结构已经够用，零改动。** 经验住 `knowledge` 表、经历住 `episodes` 表、
日志住 `logs` 表——「一张表一类」本来就是 v4 的样子，`kind` 列只是历史标签（见 7.2）。
所以 8 个存量库一个字节都不用动，也没有 v5。

### 7.1 字段（v4 已全部落地，无新增）

| 表           | 字段                 | 类型                | 用途                     |
| ----------- | ------------------ | ----------------- | ---------------------- |
| `knowledge` | `forget_level`     | INTEGER DEFAULT 3 | 0~N（N 由配置决定）           |
| `knowledge` | `confidence`       | REAL DEFAULT 0.3  | 0~1                    |
| `knowledge` | `activity`         | REAL DEFAULT 0    | 本周期加权累加                |
| `knowledge` | `period_start`     | INTEGER           | 本周期起点                  |
| `knowledge` | `last_verified_at` | —                 | **复用现有 `verified_at`** |
| `knowledge` | `level0_since`     | INTEGER（可空）       | 落到 0 级的时刻，见下方说明        |
| `episodes`  | `forget_level`     | INTEGER DEFAULT 3 | 0~N                    |
| `episodes`  | `activity`         | REAL DEFAULT 0    | 同上                     |
| `episodes`  | `period_start`     | INTEGER           | 同上                     |
| `episodes`  | `revive_hits`      | INTEGER DEFAULT 0 | 0 级复活计数                |
| `episodes`  | `level0_since`     | INTEGER（可空）       | 同 `knowledge`          |
| `episodes`  | `confidence`       | —                 | **派生，不存**              |

**`level0_since` 为什么是独立字段**：`level0_purge_days` 要判的是"在 0 级**停留**了多久"，
而 0 级本身不参与周期裁定，`period_start` 会停在降级那一刻——能算出结果，但那是**隐式约定**，
一旦以后给 0 级加了别的周期动作就会破。单独存一个"进入 0 级的时刻"，
判定变成 `now - level0_since > level0_purge_days`，一个字段换掉一条靠巧合成立的隐式规则。
升回 1 级时置回 NULL。

`memory_events` 表做审计，也在 v4 里了。

### 7.2 现有字段的处置

| 现有                                 | 处置                                                                                                                    |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `knowledge.kind` / `episodes.kind` | **历史标签，代码不再读写**。旧库留着（`NOT NULL`，默认值分别 `'knowledge'` / `'narrative'`），所以新代码省略该列的 INSERT 走默认值，不会失败；新库不建这两列。v3 年代的 `state` / `case` 就地读作**经验 / 经历**，不做改写 |
| `access_count`                     | 保留（供展示），**活跃度另立 `activity`**，因为需要加权累加而非整数计数                                                                            |
| `importance`                       | 保留，新用途是**决定初始等级**                                                                                                     |
| `state_interval_days`              | **废弃**。旧文档 §3 已指出它是"复核间隔"且有迁移默认值 7.0 会伪装成"已稳定"。新库不建；旧库留着（默认 7.0），代码不读                                                         |
| `compression_level`                | 保留，与新等级联动（§3.3 表）                                                                                                     |
| `episodes.at`                      | 保留，这就是"时间戳与内容分离"的落地——**无需改动，现成满足**                                                                                    |

**为什么不为 kind 升版本**：它没有任何行为挂在上面了。为了"表里少一列"去改 8 个真实库的
schema 版本、搬一遍向量和 FTS，代价全在迁移风险上，收益只是好看。**旧库的 kind 列闲置，
新库不建列**——两种库跑同一份代码，SQL 里一个 `kind` 都不出现。

### 7.3 约束核对（重要，避免实施时踩坑）

| 触发器                                                    | 与新方案是否冲突                            |
| ------------------------------------------------------ | ----------------------------------- |
| `knowledge_content_immutable`                          | ✅ 不冲突，经验不压缩                         |
| `knowledge_no_revive`                                  | ✅ 不冲突，此处"复活"指遗忘层复活，与失效链无关           |
| `knowledge_kind_immutable` / `episodes_kind_immutable` | ✅ 不冲突，kind 不再变更——因为压根不再写。**新库不创建** |
| `episodes` 无 content 触发器                               | ✅ 正好支持经历压缩                          |
| `logs_append_only`                                     | ✅ 不受影响                              |

**结论：不需要 DROP 任何现有触发器；新库也不创建那两条 kind 触发器。**

## §8 迁移、发布与四个决定

### 8.1 存量：不需要迁移

原方案打算写个升级程序，把 `state` / `case` 重映射成两类并补初始可信度。**实测发现这一步是多余的**：
v4 的写入路径本来就是按 kind 给初值的，存量数据已经天然落在目标位置上。

**2026-11-16 实测读数**（项目库 + 全局库，直接查库，非估算）：

| 存量                                       | 归入 | 实际可信度           | 实际等级 | 要不要动  |
| ---------------------------------------- | -- | --------------- | ---- | ----- |
| `knowledge.kind='knowledge'` 22 条（全局 93） | 经验 | `0.6`（全部一致）    | ~4.0 | **什么都不用做** |
| `knowledge.kind='state'` 22 条（全局 1）      | 经验 | `0.3`（全部一致）    | ~4.0 | **什么都不用做** |
| `episodes.kind='case'` 21 条               | 经历 | 派生（不存）          | ~3.9 | **什么都不用做** |
| `episodes.kind='narrative'` 9 条           | 经历 | 派生（不存）          | ~4.0 | **什么都不用做** |

合计：经验 63 条（含已失效 9 条）、经历 30 条（`narrative` 均已 `compression_level=1`）。

**为什么刚好对上**：`0.6` / `0.3` 不是迁移时填的，是 v4 写入时就按 kind 定的初值——
`kind='knowledge'` 写 0.6、`kind='state'` 写 0.3。原方案要的"机制性内容起点高、易变内容压低起点"
本来就是既有行为，只是当时用 kind 表达，现在改用「初始可信度」表达。**语义换了承载方式，数值没变。**

**所以的迁移动作是零**：

- 不建 v5、不升 `schema_version`（仍是 4）
- 不搬向量、不重建 FTS
- 不改写任何一行的 `kind`（它就是历史线索，`state` / `case` 读出来即经验 / 经历）
- 不删任何存量条目，全部走新机制自然淘汰

`global.db` 的 94 条同样适用；它另有存废问题见 §8.2。

### 8.2 决定：关闭 `global.db`

**结论**：不再有 AI 自动写入的全局库。`scope="global"` 失效，`memory_promote` 下线。

**理由**：

- 全局库是**公有空间，没人审核**。AI 一次错误决策会污染所有项目，而跨项目污染比单项目污染难排查得多——你在 A 项目看到一条"结论"，实际是 B 项目里 AI 臆断的。
- 真正该跨项目共享的内容，本来就属于**信条**（硬约束、工作方式），应该进 `CORE_RULES.md` 静态注入，而不是躺在向量库里等着被检索。
- 剩下那些"跨项目但不硬"的内容，绝大多数其实只属于某一个项目。留在项目库更准确。
- 少一套生命周期、少一份要迁移的库、少一类"这条为什么在全局"的困惑。

**迁移步骤**（不物理删文件）：

1. 导出全局库全部 live 条目（当前 51 条）。
2. 人工分拣三类：**进 `CORE_RULES.md`** / **分派到对应项目库** / **丢弃**。
3. 关闭 `scope=global` 写入路径；`memory_promote` 改为「提升到信条」或直接下线。
4. 原文件改名 `global.db.retired-2026xxxx`，保留至少一个季度再考虑删。

**2026-11-17 已执行**（第 12 项）：

| 步骤 | 结果 |
| --- | --- |
| 导出 | `~/.humanity-memory/retired-global-20261117.md`（62 KB，94 条全文，按有效/失效分组）<br>`retired-global-20261117.json`（112 KB，原始字段） |
| 关闭写入 | `scope="global"` → `ScopeError`（提示语直接指向 CORE_RULES）；`memory_promote` 保留工具壳子但恒回报「已下线」 |
| 停止打开 | `MemoryStore` 不再 `open_db(layout.global_db)` —— 打开就会顺手建一个空库，等于把刚关掉的又造回来 |
| 留档 | `global.db` → `global.db.retired-20261117`（1.0 MB，含 51 有效 / 43 失效） |
| 顺带删除 | `limits.global_experience_warn` 配置键、`stats.global_experience*` 两个字段、`GLOBAL_SPECS` 常量、四处 `db_name == "global"` 死分支 |

`CORE_RULES.md` 不受影响：它是**信条**（静态注入），不是向量库。
`rules_append(scope="global")` 仍然可用 —— 跨项目硬约束该走这条，不该走检索。

#### 偏离怎么发生的（2026-11-17 复盘）

关闭时对 51 条有效条目做了一次分域统计：

| 落在哪个域 | 条数 |
| --- | --- |
| Unity / C# / 编辑器 API | 23 |
| Unity UI 与业务细节（`LoopListView` / `ContentSizeFitter` / `CanvasGroup` / `Localization.Refresh` / 数值滚动…） | 24 |
| 本机工具链与环境（沙箱、`.workbuddy`、本工具自身的边界） | 4 |
| **真正不依赖任何具体技术栈** | **≈3** |

也就是说：它实际是**某个 Unity 项目的经验备份，只是放在了全局位置**。

**根因不是"内容质量差"，是判断主体错了。** 写入时问的是"这条重要吗"，而这个问题在项目上下文里
必然答"重要"——对一个正在做该项目的模型来说，`ContentSizeFitter` 在编辑器非 Play 下不刷新
就是它每天要用的"通用知识"。**让 AI 在项目上下文里判断"这条够不够跨项目通用"，它永远判成通用。**

所以"提升到全局"这件事，不该由一次现场判断决定。

#### 将来重新引入时的形态（用户 2026-11-17 定调）

原话：**「相关功能可能后续会重新加上，但功能会更机械。」**

这一句是硬约束，记在这里防止下次又长回"AI 自由写入"的形态。要点只有一条：
**归属由规则决定，不由模型现场判断。** 可选方向（尚未拍板，不要提前实现）：

| 方向 | 机械在哪 |
| --- | --- |
| 显式标记才算 | 只有带 `cross-project` 这个 tag 的条目才进共享区，模型想写就自己打标，等于自己承认"我认为它跨项目" |
| 白名单 + 人工分拣 | 共享区只读，AI 只能往「候选区」写，定期由人搬 |
| 结构化模板 | 共享内容不做自由文本，只收 schema 化的固定字段（约束 / 触发条件 / 反例），写不进去的就不够通用 |
| 干脆不共享 | 维持现状，跨项目只走 CORE_RULES |

**无论走哪条，都不能是「模型觉得通用就写进去」。** 那是这次偏离的唯一成因。

**如果日后确实需要跨项目共享**：改用 CORE_RULES（静态注入）或显式指定的共享库，不再用"AI 自动往里写"的模型。

### 8.3 决定：0 级删除与归档删除分开配置

`level0_purge_days`（遗忘层 → 删除）与 `archived_purge_days`（归档 → 删除）是两个独立键。  
出厂值都写 180，但**语义不同、生命周期不同，必须能分别调**。合并成一个键会在某天导致"调了遗忘层，归档策略也变了"。

### 8.4 决定：历史库升级走独立 CLI，主程序不做适配

**结论**：`humanity_memory` 的运行时（`open_db` / `store` / `lifecycle` / MCP tools）里**不出现任何历史格式适配代码**。版本不符 → 拒绝服务，升级交给一个**不对 AI 开放**的 CLI 子命令。

#### 主程序的义务只有「检测 + 拒绝」

| 允许                           | 禁止              |
| ---------------------------- | --------------- |
| 读 `meta.schema_version` 判断版本 | 改名、移动库文件        |
| 版本不符时**报错退出**并打印升级命令         | 建表、补字段、跑 DDL 修补 |
| 空文件/新目录时初始化新库                | 迁移、清洗、猜测旧字段含义   |

拒绝而不是降级运行，这一条不能松：一旦主程序能"凑合读旧库"，适配分支就会长回来。

检测规则要按最小面写（只判断，不修改）：

```text
有 meta.schema_version  → 读它，与期望版本比对
无 meta 但有 facts 表    → 视为 v2
文件不存在/空库          → 初始化当前版本
```

#### 为什么现在这版必须删

`db.py:291 open_db` 每次都先调 `retire_legacy_db(path)`，而这个函数会 **rename 库文件**；  
接着 `ensure_schema` 跑一串 DDL、`set_meta` 写一行。也就是说：

> **任何一条读路径**（`stats`、`search`、`starmap`，甚至只是看一眼）打开库，都会产生不可逆的磁盘副作用。

三个具体风险：

- 多进程同时启动（本项目高频）时会互相撞 rename，Windows 上直接 `WinError 32`
- 失败时静默留下一个孤儿 `facts` 表在库里，半年后没人知道该不该删
- 只想读一眼，却被迫接受一次文件改名——**读操作不该改磁盘**

这不是 bug，是"程序内做适配"这个决策本身的必然后果。所以按本节结论，`retire_legacy_db` 整个函数删除。

#### 五条边界（照抄星图那套）

`starmap.py` 的模块头已经写定了一套边界，升级器直接沿用——它和星图是同一类东西：**离线、只认文件路径、产物单一**。  
只把星图那条"绝不写库"改成"绝不碰源库"。

| # | 边界                                                                               | 理由                                                      |
| - | -------------------------------------------------------------------------------- | ------------------------------------------------------- |
| 1 | **只在 CLI 使用，不注册 MCP tool，不对 AI 暴露**                                              | 升级不可逆，不给模型手。同"删除是显式动作"——机器能算的事不该有不可逆的破坏力                |
| 2 | **零侵入**：不 import `db` / `store` / `models` / `lifecycle`，不依赖 `Config` / `Layout` | 旧 schema 的 DDL 与字段映射**自带字面量**。升级器是冻结的快照，永远按写它那天的规则理解旧数据 |
| 3 | **源库只读**：`sqlite3.connect(..., mode=ro)`，不 rename、不就地改                           | 源文件永远在，失败直接重跑，不需要事务回滚                                   |
| 4 | **`--out` 不给默认值**：给了才写，不给只报                                                      | 默认行为是"预览会变成什么样"，不是"悄悄产出文件"。与星图 `--out` 必填同源             |
| 5 | **一个跨版本一个模块**                                                                    | 避免 N×N 两两转换器；每个跨版本一个文件，runner 按链依次调。目前只有 `v3_to_v4`，v4 就是当前版本 |

第 2 条是最容易被妥协、也最不能妥协的一条。重复几十行常量（表名、字段名、维度）换来的是：  
**主程序怎么改都不会让升级器失效。**

#### 形态：和 `starmap` 并列的子命令

```text
src/humanity_memory/upgrade/
  __init__.py       # runner：读源库版本 → 按链调用 → 汇总报告
  v3_to_v4.py       # 单步转换，自带 v3 的 DDL 与字段映射快照
  inplace.py        # 就地替换层：唯一允许动源文件的模块（见下）
```

```bash
# 预览：源库一个字节不动，只报会变成什么样
humanity-memory upgrade <旧库路径>

# 真写：产物是新库，源库原样保留
humanity-memory upgrade <旧库路径> --out <新库路径>

# 一步到位：产出 → 校验 → 原件留档 → 替换
humanity-memory upgrade <旧库路径> --in-place
```

输入跟星图一样，接受 `.ai_memory/`、项目根，或直接给 `workspace.db`——**拖进去就行**。

#### 拖上去就升：`upgrade.bat`

星图是「把目录拖到 `starmap.bat` 上出图」，升级器照同一套：把库（或 `.ai_memory`、或项目根）
拖到 `upgrade.bat` 上，就地升好。两个 bat 的入口解析是同一段代码——发布态优先，兜底源码态：

| | `starmap.bat` | `upgrade.bat` |
| --- | --- | --- |
| 入口解析 | `release/current` → 兜底 `.venv` | 同左 |
| 默认行为 | 出 HTML，**只读** | 就地换库，**有写** |
| 拖多个文件 | 只取第一个 | 逐个跑，任一失败就置 fails |
| 结束动作 | 自动打开 HTML | `pause`，把报告留在窗口里 |
| 风险 | 无 | 先转换后校验，全过才换；原件 `.v3-<stamp>` 留档 |

`--in-place` 是**叠加层**，不是把「源库只读」作废。两层各管一段，界线不能糊：

| 层 | 能做 | 不能 |
| --- | --- | --- |
| `run()` 转换器 | 只读源库、产出新文件、自校验 | 改名、删除、就地改 |
| `run_inplace()` | 在**校验全过之后**改名留档 + 顶上 | 在转换/校验通过前动源库一个字节 |

顺序不能换：先产出并核完三件事，再换文件。这样"失败不需要回滚"的性质仍然成立——任何一步
失败都停在替换之前，线上库一个字节没动。

Windows 上还有一条物理约束：**只要有任何进程开着库文件，rename 必失败**。所以就地升级先
改名探一次占用，当场回一句"关掉客户端再拖"，而不是让用户等完整个转换才看到 `OSError`；同理
WAL 必须先 `checkpoint(TRUNCATE)`，折不全就直接停手——否则换文件会丢掉未归并的那部分。

#### 同包 ≠ 同生命周期

读到这里会撞上一个表面矛盾：前半说"程序内不做适配"，这里又把升级器放进包里。不矛盾，要区分两条路径：

|         | 运行时路径                                    | 离线路径                |
| ------- | ---------------------------------------- | ------------------- |
| 例子      | `open_db`、`memory_search`、`memory_judge` | `starmap`、`upgrade` |
| 每次请求都跑  | 是                                        | 否，人手动敲              |
| 允许知道旧格式 | **绝对不行**                                 | 可以，且必须自带快照          |
| 失败代价    | 用户当场看到报错                                 | 白跑一次，文件还在           |

`retire_legacy_db` 的问题不是"它知道旧格式"，而是它**挂在每次打开连接的路径上**——连读一眼都触发。  
升级器在同一个 wheel 里，但不在任何请求的路径上。**引擎里塞修旧引擎的代码不行，工具箱里放一把扳手没问题。**

#### 迁移完必须核三件事

| 检查       | 期望                              |
| -------- | ------------------------------- |
| 条数对齐     | 旧库 live 条数 = 新库条数 + 明确报告丢弃的条数   |
| `at` 未漂移 | 随机抽 10 条对比 `at` 原值，压缩/迁移不得改写时间戳 |
| 向量可搜     | 抽查 3 条语义检索能命中自己（未重算向量的要标明）      |

第三条容易被跳过：向量是 blob，字段搬过去了不等于可检索，维度不匹配会静默返回空结果。

#### 换 schema 是「全机器动作」，不是单库动作

`mcp.json` 是**用户级**配置，所有项目共用同一个入口。所以版本闸门一旦收紧，
受影响的是这台机器上**每一个** `<项目>/.ai_memory/workspace.db`：

```text
只升当前项目库  →  入口指向 v4  →  其它项目一开记忆就 SchemaVersionError（退出码 3）
```

库里有多少个库，就有多少个需要升级。单个库走 `upgrade.bat`，整机走 `tools/upgrade_all.py`
——后者只做「找库 / 循环 / 汇总」，「转换 → 校验 → 留档 → 替换」全部委托给同一个
`run_inplace()`，免得两份逻辑哪天走岔：

| 步骤 | 动作 | 为什么必须是这个顺序 |
| --- | --- | --- |
| 1 | 改名探占用 + `PRAGMA wal_checkpoint(TRUNCATE)` | 有进程开着就必然换不掉文件，早拒绝；WAL 不折进主文件，`mode=ro` 的读会漏数据 |
| 2 | `mode=ro` 产出 v4 副本 + 三项校验 | 校验在替换**之前**，失败时线上文件一个字节没动 |
| 3 | 原件改名 `.v3-<stamp>` 留档，副本顶上 | 回退就是改回来 |
| 4 | 重新 `mode=ro` 读版本 | 别信"应该没问题"，验线上文件 |

工具默认干跑，`--apply` 才动；`--skip <片段>` 排除指定库（如待清空的备份项目）。

> **配套的坑**：升级期间若还有旧版 exe 活着，它打开 v4 库时不会报错，而是把
> `meta.schema_version` **静默写回 3**，把库变成「结构 v4、标签 v3」的废库。
> 所以换 schema 之前先下线发布闸门并确认没有旧进程，否则升级等于白做。

### 8.5 决定：release 目录放打包产物，所有进程只跑 exe

**结论**：源码树是**开发态**，发布根下的 exe 是**生产态**。MCP server 指向 exe，不指向源码。
代码改多少都不影响生产——**唯一生效路径是「重新打包并发布」**。

发布根**固定住在项目目录树外**：默认 `%LOCALAPPDATA%\HumanityMemory\release`，
可用 `HM_RELEASE_ROOT` 覆盖。这不是整理癖，是硬约束，理由见下方「发布根必须住在项目树外」。

这是最彻底的"发布闸门"：不靠配置、不靠分支、不靠开关，靠**两个不同的可执行文件**。

#### 三层隔离，exe 负责最硬的那层

| 层 | 源码态 | release 态 |
| --- | --- | --- |
| Python 代码 | 改完下次重启生效 | **冻结在打包那一刻**，源码改了也不变 |
| 第三方依赖 | 跟着 venv 漂 | 锁死在 `_internal/`，连 Python 版本都锁住 |
| 资源文件 | 读 `src/humanity_memory/schema.sql` | 打包内嵌，随 exe 一起冻结 |

最后这条顺带解决一个老问题：不再依赖"对方机器上 pip 装对了版本"。分发时给一个目录就能跑。

#### 目录结构：必须版本化

```text
<发布根>/                        # 默认 %LOCALAPPDATA%\HumanityMemory\release，**不在项目树内**
  v{ver}/                # 目录名取 pyproject.toml 的 version，下例 v0.3.0 仅为示例
    humanity-memory.exe
    _internal/            # onedir 依赖（含 sqlite_vec 的 dll）
    build.json            # git sha、时间、PyInstaller 版本、pip freeze 快照
  v{old}/                 # 旧版本一地留着，只增不自动清
  v{ver}.stale-{ts}/      # 同名版本被覆盖前改名留档，不删（删要人确认）
  .staging-{ts}/          # 打包中间目录，产物搬走后为空即自动回收
  current/                # 目录 junction → 当前生效的 v{ver}/，mcp.json 只认这个路径
  current.txt             # 一行文本，与 current/ 指向同一版本，供脚本与 bat 读
  history.json            # 版本栈，--rollback 据此找上一版
  .env                    # 跨版本共享的凭据（不在版本目录里，回滚不换凭据）
  backups/
    workspace.pre-v{ver}.db   # 每次发布前的库快照
```

#### 发布根必须住在项目树外（实测踩过，不是理论洁癖）

宿主沙箱限制**「从工作区树内启动的进程」写工作区外的路径**。exe 放在项目里，
它就连 `~/.humanity-memory/global.db` 都打不开，报 `attempt to write a readonly database`；
`serve` 在握手前退出，客户端看到的就是 **`MCP error -32000: Connection closed`**。

2026-11-16 用同一份 exe 换个位置跑，行为如下：

| exe 所在位置 | 写 `~\.humanity-memory` | `doctor` |
| --- | --- | --- |
| `D:\Wrok_proj\HumanityMemory\release\v0.3.0\`（项目树内） | ❌ `WinError 5` | `readonly database` |
| `D:\Wrok_proj\HumanityMemory\build\exe-copy\`（换个项目内子目录） | ❌ | `readonly database` |
| `D:\Wrok_proj\HumanityMemory-release\`（项目同级，**名字仍同前缀**） | ❌ | `readonly database` |
| `D:\Wrok_proj\HM-release-probe\`（不同前缀） | ✅ | 全绿 |
| `%LOCALAPPDATA%\HumanityMemory\release\`（**最终选它**） | ✅ | 全绿，embedding 真调 227ms |

前三次失败排除了「权限不够」这类解释：同一个文件、同一个用户、ACL 里 `nino` 是 FullControl，
`python.exe` / PowerShell 写同一位置都正常，只有这个 exe 不行。**按前缀匹配**这一点也验证过——
`HumanityMemory-release` 与 `HumanityMemory` 同前缀就仍然被拦。

因此 `build_release.py` 里有一条**硬校验**：发布根落在项目树内（或同名前缀）直接报错退出，
不给人"看起来发布成功、实际连不上"的机会。

`schema.sql` / `vec0` 那条同理——它们随 exe 走，exe 在哪都能读到自己的 `_internal/`。
唯一受影响的是**写**：全局库、库快照、`.env` 之外的运行期写入，全部发生在项目外。

#### 打包目录必须和产物同盘

产物最终要 `rename` 成 `v{ver}/`。同盘 rename 是原子的；跨盘时 `shutil.move` 会退化成
「整体复制 + 删源目录」，一次删 150+ 个文件，**撞上批量删除保护钩子**（实测拦过一次发布，
且是在产物已经搬完、smoke 还没跑的空档里断的）。
所以 PyInstaller 的 `--distpath` 指向 `<发布根>/.staging-{ts}/dist`，`--workpath` 留在项目 `build/`。

**为什么不能固定路径覆盖**：exe 在运行时**被 Windows 锁定**，覆盖会 `WinError 32`——
和 `retire_legacy_db` 踩的是同一个坑。所以产物必须版本化。

但"产物版本化"和"可回退"是两件事，中间那根链条是**入口**。如果 mcp.json 直接写
`<发布根>/v{ver}/humanity-memory.exe`，每次发布和回滚都要改客户端配置，就没有单一真相；
`current.txt` 又只有 bat 和脚本会读，于是"回滚 = 改那一行"名不副实。
所以入口固定在 `<发布根>/current/`——它是个**目录 junction**，指向当前生效的版本目录。

#### 回退：入口稳定、产物版本化、数据同步

「发布出错回不去」不是一个问题，是三层。拆开才治得干净：

| 层 | 症状 | 病根 | 治法 |
| --- | --- | --- | --- |
| 入口 | 回滚要手改 mcp.json + 重启，且没有单一真相 | mcp.json 写死具体版本路径 | `<发布根>/current/` junction，mcp.json 永指它 |
| 产物 | 旧目录一删，就再也造不出同一个二进制 | 发布根不入库；用旧 sha 重打也 ≠ 原件（依赖、PyInstaller 版本都会漂） | 版本化目录**只增不自动清**；`build.json` 记 `pip freeze` 与 PyInstaller 版本，至少能重建等价物 |
| 数据 | 代码退了，旧 exe 打不开新库 | 新 exe 写过 `schema_version=4` 的库，旧 exe 按"不符即报错"直接拒开 | 发布前 `.backup` 库快照，回滚时一并还原，并**明确告知会丢多少写入** |

**junction 为什么比"改路径"强**：Windows 锁的是被执行的那个 exe 文件。
目录 junction 只是个 reparse point，`rmdir current` 再 `mklink /J` 随时能换，
不碰目标文件、不需要管理员权限（`/J` 与 `/D` 的区别就在这里）、不产生 `WinError 32`。
`current/` 与 `current.txt` 始终指向同一版本：前者给操作系统解析，后者给人和脚本读。

**`--rollback` 做什么**：读 `history.json` 找上一版 → 换 junction + `current.txt` →
还原对应库快照（`schema_version` 不匹配就停下要求确认，并报出"会丢最近 N 次写入"）→
跑 smoke test → 提示重启客户端。

**发布必须自带回滚演练**：`--publish` 走完 → `--rollback` 回上一版 → smoke 验旧版仍可用 →
再 `--publish` 回来。演练过的才叫回滚；没演练过的只是"希望它能用"。
手搓 `mklink` 的路径真出事时没人敢碰，所以这条不做就不能算发布链路跑通。

**首次发布是特例：没有上一版可退。** 所以第一次 `--publish` 只产出 `<发布根>/v{ver}/` 并跑 smoke，
**先不切 junction、不动 mcp.json**——生产此刻仍然跑源码态，天然安全。
确认可用后再切；切换那一刻的"回滚目标"是源码态本身（白名单唯一一次合法使用）。
从第二次发布起才有真正的版本栈可退。

#### 发布脚本的动作

`tools/build_release.py`（互斥四选一，实现已落地）：

| 动作 | 干什么 |
| --- | --- |
| `--publish` | 备份库 → 打包 → smoke；首次发布只产出不切换 |
| `--promote` | 把 `current` junction 切到指定/最新版本，必要时改写 mcp.json |
| `--rollback` | 回上一版：换 junction +（默认）还原库快照 + smoke 验旧版 |
| `--status` | 当前版本、历史、库快照、mcp.json 现状 |

常用开关：`--force`（覆盖同版本目录，先停客户端）、`--no-switch`（只打包）、
`--keep-db`（只退 exe 不动库）、`--yes`（跳过确认）。

`--publish` 的五步：

1. **备份库**：`.backup` 出 `<发布根>/backups/workspace.pre-v{ver}.db`，删掉继承来的
   `-wal`/`-shm`（快照应当是单个自洽文件），记下当时的 `schema_version`
2. 读 `pyproject.toml` 的 `version` 作为**唯一版本真源**，打包到 `<发布根>/.staging-{ts}/dist`，再同盘 rename 成 `v{ver}/`（onedir，**不用 onefile**）。
   本文出现的 `v0.3.0` 只是**示例**，实际目录名一律以 `pyproject.toml` 当前值为准
3. 写 `build.json`（git sha / 时间 / PyInstaller 版本 / pyproject 版本 / `pip freeze` 快照 / `schema_version`）
4. `.env` 就位后**跑 smoke test**；不过就**改名成 `.stale-{ts}` 留档**并退出非 0
   （不删：既要能人工排查，也不要触发批量删除的保护钩子）
5. 切 junction + 更新 `current.txt` + 追加 `history.json` → 提示重启客户端。
   **mcp.json 只改一次**（从 `.venv` 迁到 `current/`），此后发布不再碰客户端配置

选 onedir 不选 onefile：onefile 每次启动解压到 temp，冷启动慢（stdio 场景首轮响应会拖），
且更容易被杀软误报。

**smoke 必须跑在仓库内**（`build/smoke-{ts}/`，跑完清掉）。两个原因：
这台机器上 `%TEMP%` 与用户目录对**新编译的无签名 exe** 是拒写的（`WinError 5`，
源码态 python 却可以），拿系统临时目录做 smoke 会得到假失败；而"在项目目录里跑"
本来就是生产姿势，顺带验到 cwd 解析。

**版本号有两处**，`pyproject.toml` 与 `src/humanity_memory/__init__.py` 的 `__version__`
都要改——冻结态的 `doctor` 打印的是后者。忘了会得到一个"目录叫 v0.4.0、自报 0.3.0"的包。

#### 打包前必须先修的五处路径

这些地方都用 `__file__` 反推项目结构，源码态成立、冻结后必然错位。行号已逐个核对（2026-11-16 实测）：

| # | 位置 | 现在 | 冻结后 | 改法 |
| --- | --- | --- | --- | --- |
| 1 | `db.py:15` | `Path(__file__).with_name("schema.sql")` | 依赖 `--add-data` 才能同目录共存 | 走 `resources.py` |
| 2 | `db.py:43` | `parents[2] / "tools" / "bin"` 找 `vec0.dll` | 路径不存在 | 直接用 `sqlite_vec.loadable_path()` |
| 3 | `config.py:83` | `parents[2] / ".env"` | 找不到，凭据全空 | **frozen 走 `<发布根>/.env`**，源码态不动 |
| 4 | `starmap.py:136` | 同第 2 条 | 同上 | 同第 2 条 |
| 5 | `starmap.bat` | 硬编码 `.venv\Scripts\humanity-memory.exe` | 双击跑的是源码态旧代码 | 指向 `release\current\humanity-memory.exe` |

第 2~4 条不是"打包引入的问题"，是本来就有的耦合：这个包默认自己住在 `<项目>/src/humanity_memory/`，
一旦 `pip install` 到 `site-packages`，`parents[2]` 就是 `Lib/`，`.env` 早就找不到了。
exe 化只是把它逼到台面上。第 5 条属于同一个病的另一面：发布之后还有人从源码态入口启动，
就等于发布闸门漏了一个洞。

**第 3 条别改成反方向。** `config.py:80` 的注释写得很清楚，当初是**刻意**不叠加 `cwd/.env` 的——
「配置加载与启动目录彻底解耦，避免 cwd 漂移让凭据静默失效」。而 exe 的 cwd 由 MCP 客户端决定，
比源码态更不可信。所以不是"改从 cwd 解析"，而是：

| 形态 | `.env` 来源 | 理由 |
| --- | --- | --- |
| 冻结 | `Path(sys.executable).resolve().parent.parent / ".env"` → `<发布根>/.env` | 跨版本共享一份，不必每版复制；`resolve()` 会穿过 junction，回滚不影响凭据 |
| 源码 | 保持 `parents[2]` | 现状成立，不动 |

注意是 `.resolve().parent.parent`：`sys.executable` 拿到的是启动路径 `<发布根>/current/humanity-memory.exe`，
`resolve()` 后才落到 `<发布根>/v{ver}/`，再上一级才是 `<发布根>/`。少一层 `resolve()` 就会读 `current/.env`（跟着版本飘）。

两者都不看 cwd。真要覆盖凭据，走 `mcp.json` 的 `env`（本来就是最高优先级）或 `HM_*` 环境变量。

**第 2、4 条有现成 API。** wheel 里自带 `sqlite_vec/vec0.dll`（已确认），
直接 `conn.load_extension(sqlite_vec.loadable_path())` 即可，打包内外同一套逻辑。
`db.py:_candidate_extensions` 那套"猜三个目录"可以整体退役，不必靠 `--collect-all` 再自拼路径。

新增一个 `resources.py` 统一回答"内置资源在哪"：

```python
def resource(name: str) -> Path:
    if getattr(sys, "frozen", False):
        # onedir 下 _MEIPASS 即 _internal/，必须与 --add-data 的目标前缀一致
        return Path(sys._MEIPASS) / "humanity_memory" / name
    return Path(__file__).parent / name        # 源码态：src/humanity_memory/<name>
```

源码分支**不能再拼一层** `humanity_memory`，否则就成了
`src/humanity_memory/humanity_memory/schema.sql`。打包参数固定写成
`--add-data "src/humanity_memory/schema.sql;humanity_memory"`，两边才对得上。

#### mcp.json 只改一次，之后永远指向稳定入口

现在 `~/.workbuddy/mcp.json` 里**根本没有 exe 路径**：

```json
"command": "D:/Wrok_proj/HumanityMemory/.venv/Scripts/python.exe",
"args": ["-m", "humanity_memory.mcp_server", "--token", "....token.json"]
```

首次从源码态切到 exe 时要整体重写（不是"改一行路径"，因为原内容里没有路径可改）：

```json
"command": "%LOCALAPPDATA%/HumanityMemory/release/current/humanity-memory.exe",
"args": ["--token", "....token.json", "serve"]
```

注意是 `current/`，**不是** `v{ver}/`——这是回滚能只动一处的前提。
此后每次发布都只换 junction，mcp.json 一个字节都不动。

**`--token` 必须写在 `serve` 前面。** 它是全局参数（定义在子命令之前），
写成 `serve --token x` 时 argparse 直接 `unrecognized arguments` 退出，
客户端看到的就是 `MCP error -32000: Connection closed`——2026-11-16 实际踩过这一发，
现在 `build_release.py` 生成的是 `["--token", tok, "serve"]`，这次顺序错了就起不来，很好查。

`serve` 子命令已经存在（`cli.py:709`），不用新造 `mcp` 入口，也不要把 `-m humanity_memory.mcp_server`
原样留在 args 里——那个 exe 不认识 `-m`。
发布脚本只在检测到配置**还没指向 `current/`** 时才改写，并把改动 diff 打出来让人确认；
`MCP_JSON` / `ENTRY` 两个常量在 `tools/verify_mcp_config.py:31` 已有，复用它们，
别出现第三处硬编码的 `~/.workbuddy/mcp.json`。

**发布后必须真握手一次**，不能只看 `doctor`：`doctor` 不 import `mcp_server`，
`serve` 挂掉它照样全绿。`tools/build_release.py` 的 smoke 已内建
`initialize` + `notifications/initialized` + `tools/list` 三步，实测拿到 25 个工具才算过。

#### 和 §8.4 的关系：一条约束变成物理事实

§8.4 要求升级器自带旧 schema 快照、不 import 主包——那时是**靠自律**保证的。
打进 exe 之后，这条约束**自动成立**：发布出去的 exe 永远不会变，它理解旧 schema 的能力就冻结在发布那一刻。

反过来要补一条明文规矩，但**不是"保留旧版本 exe"**。发布根下一个版本五十来兆，显然不入库，
换台机器手上就只剩最新 exe，老库再也升不动——"留着旧 exe"只是本机巧合，不是约束。

> **`upgrade/` 下的迁移模块只增不删。** `v3_to_v4.py` 几百行，永久留在包里，
> 任何新版 exe 都能升任意老库。

这比依赖旧二进制靠谱得多，也让"自带旧 schema 快照"从自律变成一条可 grep 的规矩：
`ls src/humanity_memory/upgrade/` 应当能看到每一次历史迁移。

#### 代价，说实话

| 代价 | 说明 |
| --- | --- |
| 打包耗时 | 每次 30~60 秒，目录约 50MB |
| **发布链路变长** | 打包 + smoke + 回滚演练，一轮约 2~3 分钟。省掉演练就等于省掉了回滚能力，不能省 |
| **回滚会丢写入** | 库快照是发布那一刻的。回滚 = 回到那一刻，中间的记忆写入作废；所以要报出条数让人决定，而不是静默还原 |
| 调试变难 | 生产出问题得回源码态复现，现场只有日志 |
| 原生扩展易漏 | `sqlite_vec` 的 dll 漏了就启动即废，`sqlite_vec.loadable_path()` + `--collect-all` 兜底 |
| **必须 smoke test** | 发布后跑一次 `humanity-memory.exe doctor`，否则可能发一个连不上 vec0 的废包 |

最后一条不要省，而且**"全绿"不构成通过条件**。exe 的失败模式和源码态不同：
源码态缺 dll 会抛清晰的 ImportError，冻结态可能只是 `doctor` 里静默降级。
实测 `cli.py:371` 的 embedding 检查返回的是：

```python
{"check": "embedding", "ok": True, "detail": "未配置，退化为关键词检索"}
```

`ok` 是 `True` —— 它**是绿的**。所以 doctor 全绿这件事，在一张确实坏掉的包上同样成立。
发布脚本必须解析 `detail` 字符串、命中"未配置"就判失败并删掉产物，不能靠人看一眼颜色。

#### 界线重申

`<发布根>/current/` 是**唯一**的常态生效入口。别再引入：

- ❌ 代码里的 `[release] mode = "v3" | "v4"` 开关
- ❌ 一个能看到两套逻辑的分支
- ❌ "先发一半，剩下靠配置补"
- ❌ 删掉 `upgrade/` 里的历史迁移模块（删了就等于放弃了升级老库的能力）
- ❌ 把 mcp.json 指到 `v{ver}/` 或 `.venv` 的常态配置（一写死就没有单一真相，回滚也跟着复杂）
- ❌ 让 `starmap.bat` 继续指向 `.venv`

**唯一白名单例外：应急通道。** 打包**本身**坏掉时（依赖升级后 PyInstaller 打不出能跑的包），
手上没有任何可用产物，生产会直接停摆。此时允许把 mcp.json 临时指回 `.venv` 源码态，
**仅限回滚 / 排障期间**，恢复后必须切回 `<发布根>/current/`。

判据很硬：只有 `build_release.py` 打不出可用包、且 `--rollback` 也救不回来时才启用；
"exe 有 bug"不算——那是正常回滚的范畴。写在这里是为了它发生时有据可依，
而不是悄悄长成第二条常态路径。

**配置管参数，二进制管结构。** 想改结构就打包发布，这是唯一的路。

## §9 与旧方案的差异（供对照）

| 维度    | 旧（schema v3 + consolidate-stability）    | 新（本方案）                     |
| ----- | --------------------------------------- | -------------------------- |
| 分类    | 四类：knowledge / state / case / narrative | **两类**：经历 / 经验             |
| 分类方式  | 判据写在 prompt，模型当场判                       | 仅一个判据：是否需要"发生时刻"           |
| 易变性   | 靠 kind 区分（state 短 TTL）                  | 靠**可信度**区分（连续值）            |
| 复核    | 到期全部逐条 `matched`，每天固定开销                 | 只验可信度低的，且**只在被读到时**        |
| 遗忘    | TTL + 访问次数                              | 等级阶梯 + 周期活跃度               |
| 遗忘后   | 归档，可查回                                  | 0 级遗忘层，**可被深度回忆复活**        |
| 加分    | `reinforce` 固定 +0.2×剩余                  | 按**间隔**成超线性，间隔越久越值钱        |
| 谁决定分值 | 模型（隐含在判断里）                              | **工具按公式算**，模型只报 bool + 证据级 |
| 谁决定升降 | 模型（复盘时自己定 level）                        | **SQL 阈值比较**，零 token       |
| 参数位置  | `config.py` 里的 Python 常量                | **TOML 文件**，代码零字面量         |
| 等级档位  | 固定 0~3 压缩级                              | **可配置数组**，加档不改代码           |
| 跨项目   | `global.db`，AI 可写                       | **取消**，跨项目走 CORE_RULES     |


**被继承下来的部分**（旧方案里验证有效、不能丢）：

1. 稳定 = 主动复核过，不是"没变化"
2. 典型 = 多个独立事件，不是同一条被读多次
3. 文本共现 ≠ 使用（L1/L2/L3 分级）
4. 沉默不是反证
5. 重要的事起点更详细、保持更久
6. 审计凭证不能省

| 将来重建共享区    | **允许，但必须更机械**：归属由规则决定，不由模型现场判断（§8.2 末节）                         |
| 遗忘等级档数      | **可配置扩展**，代码不写死                                                 |
| 参数存放        | **统一 TOML 文件**，不用代码常量、不用配置类                                     |
| 活跃度统计       | 周期内累加，裁定后清零（不做滑动窗口）                                             |
| 复活目标        | 1 级                                                             |
| 0 级删除        | **只出候选 + 显式确认才删**（纯自动有误删风险，纯人工会堆积）                            |
| AI 与工具的分工   | AI 只给 bool + 证据级；分值、升降、遗忘、查重归工具                                 |
| 历史库升级       | **`upgrade` CLI 子命令**（不对 AI 开放、零侵入），主程序只检测版本、不符即报错，**不含任何适配代码** |
| 历史迁移模块      | **`upgrade/` 下只增不删**。任何新版 exe 都能升任意老库，不依赖"保留旧版本 exe"（那只是本机巧合，换机器即失效） |
| 版本号真源       | **`pyproject.toml` 的 `version`**。本文出现的 `v0.3.0` / `v0.2.0` 一律是示例，打包目录名以实际值为准 |
| 生效方式         | **源码态开发、发布根 exe 生产**。改代码不生效，唯一发布动作是重新打包；入口固定 `<发布根>/current/`，mcp.json 永不动 |
| 回退机制         | **入口稳定 + 产物版本化 + 发布前库快照**。回滚 = 换 junction + 还原库（版本不符先报"会丢 N 次写入"再决定）；发布必须自带一次回滚演练，没演练不算链路跑通 |
| 应急通道         | **仅当打包本身坏掉**（打不出可用包且回滚也救不回）时允许临时切回 `.venv` 源码态，恢复后必须切回 `current/`；"exe 有 bug"不算 |
| 发布把关        | `build_release.py` **内建 smoke test**：`doctor` 的 `detail` 命中「未配置」即判失败并留档产物；外加一次真 `serve` 握手（`doctor` 不 import mcp，`serve` 挂了它照样全绿）。`ok` 恒为 `True`，只看颜色不算验过 |
| 发布根位置      | **必须在项目树外且不同前缀**，默认 `%LOCALAPPDATA%\HumanityMemory\release`（`HM_RELEASE_ROOT` 可覆盖）。宿主沙箱按前缀拦「工作区内进程写工作区外路径」，放项目里 exe 连 `global.db` 都打不开 |
| mcp.json 参数顺序 | **`["--token", tok, "serve"]`**。`--token` 是全局参数，写成 `serve --token` 会 `unrecognized arguments` 退出，客户端表现即 `Connection closed` |
| 资源定位        | 内置资源统一 `resources.resource(name)`；`.env` 冻结取 `<发布根>/.env`（`sys.executable` 穿 junction 后取上一级）、源码取仓库根，**两态都不看 cwd** |
