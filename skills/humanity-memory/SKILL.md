# HumanityMemory

跑在 SQLite + sqlite-vec 上的本地长期记忆。

## 结构：两类记忆 + 日志 + 一条信条

**判据只有一条：它是否需要回答「什么时候发生的」。**

- 需要 → **经历**（episode）：发生过的事，带时间，会随时间逐级压缩
- 不需要 → **经验**（experience）：可复用的判定与结论，不压缩，可被推翻

| 类 | kind | 存哪 | 内容 | 规则 |
| --- | --- | --- | --- | --- |
| **信条** | — | `CORE_RULES.md` | 硬约束、工作方式 | 静态注入 System Prompt，**不进向量库、不检索、不遗忘** |
| **经验** | `experience` | `knowledge` 表 | 机制、约束、接口约定、根因、踩过的坑 | 可信度靠证据涨落；被推翻时**追加新条并让旧的失效** |
| **经历** | `episode` | `episodes` 表 | 一次具体事务的过程、试错、判断转折 | 带发生时间；没有可信度（真假由事实决定）；**会逐级压缩** |
| **日志** | `log` | `logs` 表 | 当天发生的原始记录 | **只追加、不可修改**（触发器强制），复盘后清空 |

信条不需要你操心——它已经在你的系统提示里了。你主要操作后三类。

旧的四类（`state` / `case` / `narrative`）**已废弃，不要再用**：
`kind` 只接受 `experience` / `episode`，写别的会直接报错。历史上写过 `state` / `case` 的条目
现在就读作经验 / 经历——它们本来就该这样读，只是当时分了四类。

> **状态不再是一种记忆类型，而是一个数值。** 旧方案把「易变的结论」单列成 `state` 并配复核梯子
> （1→3→5→7 天），现在只用**初始可信度**表达：易变的给 0.3、一般结论 0.5~0.6、稳定的机制 0.8。
> 之后不靠日历催你复核，靠 `memory_verify` 攒证据自然涨落。少一个分类，少一套梯子。

## 落笔之前：先问三句

记忆的价值不在真，在**可迁移**。写 `memory_write(kind="experience")` 之前先回答：

1. **换个单号、换个任务 ID、换个资源名，这句话还成立吗？**
   不成立 → 它是**经历**，写 `kind="episode"`。带单号的排查过程、一次性结论都在这里。
2. **三个月后它还成立吗？**
   不成立 → 仍然可以写经验，但 `confidence` 给低（0.3 左右），让它靠后续验证自己爬上来。
   或者更干脆：只写进日志，等它真的稳定了再提炼。
3. **我能指出它在代码里的落点吗？**（哪个类、哪个方法、成立的条件）
   指不出 → **先别写**。写下来只会是一条听起来可信、拿不出证据的断语，
   比不写更危险：它会成为后续排查的锚点，把人往错方向带。

三问全过，才是经验。

## 两类东西，两个去处

| 类型 | 判据 | 例子 | 怎么落 |
| --- | --- | --- | --- |
| **经验** | 换实例仍成立 + 有代码落点 | "`ResolveTask` 末尾 `UsesScene(taskId,null)==true` 会短路兜底，所以引导卡住时不报错" | `memory_write(kind="experience", confidence=0.8)` |
| **经历** | 绑单号、绑一次事件、绑某一天 | "Bug #10805：引导不指餐厅，根因 StockBread 三条静默出口" | `memory_write(kind="episode")` |
| **日志** | 还没想清楚的原始素材 | 报错栈、时间线、原话 | `log_append` |

**同一次排查通常要写两条**：过程进经历（带单号、可回溯），可复用的结论进经验（换单号仍成立）。
这不是重复，是把同一件事的两个用途分开存——经历用来回答"那次到底怎么修的"，
经验用来回答"下次遇到同类问题先看哪"。

### 反例：同样是真话，价值差十倍

```
❌ kind=experience: Bug #10805 根因：QuestGuide.StockBread 在任务 40001 开局有三条静默出口……
```

单号和任务 ID 把它钉死在一件事上。三个月后有人问"引导 114514 为什么不触发"，
它进得了候选集，却只能是噪音——甚至会把排查方向锚到 StockBread 上。

```
✅ kind=experience: QuestGuide 排查「引导卡住 / 零提示」先看三处：各分支 return 前漏了 Tip、
   ResolveTask 末尾 UsesScene(taskId,null)==true 短路兜底、!MainIdle() 提前 return。
```

换任何单号都成立，还能指出落点——这才是经验。原案例本身不丢，写成 `kind="episode"` 存着即可。

**手软的代价是双份的**：把经历当经验写，检索时它同时做两件坏事：占掉 top-6 里的一个席位
（实测这批库里 top-6 相似度区间只有 0.07，无关项很容易挤进来），以及**锚定排查方向**——
看到"三条静默出口"就顺着想，而真实根因可能在配表。

**默认写日志。** 白天对话里绝大多数内容都应该进日志，复盘时再提炼成经验。
过早写经验会导致：记了一堆当天细节当"永久结论"，三个月后全是噪音。

> **日志的寿命只到复盘为止。**
> 复盘（`consolidate_apply(purge=true)`）会**物理清空**原始日志，之后只剩压缩后的经历。
> 所以要查精确的报错栈、完整时间线、当时的原始措辞，**必须在复盘前**查。
> 如果某天的原始记录很重要，复盘时改传 `purge=false` —— 日志会保留并标记为已复盘。
>
> 检索很便宜，别吝啬：`memory_search(..., kinds=["log"])` 只查日志层，
> `log_list(day="today")` 按天列原文，`kinds` 不传才是全部。

## 可信度：证据决定，不是感觉决定

经验写下来时你给一个 `confidence`，那只是**起点**。之后它怎么变，只取决于有没有证据。

```
memory_verify(item_id="x_xxx", ok=true, level="L1")
```

**加多少分由间隔决定**：`delta = gain_k × interval^gain_alpha × level_weight`，封顶 1.0。
隔了半年再看一眼它还是对的，比昨天刚验过今天又验一次，信息量大得多。
间隔不接受调用方传参——一律由 `verified_at ?? created_at` 算出。间隔本身就是证据，
让人传等于让人自己发证据。

| 证据级别 | 含义 | 权重 |
| --- | --- | --- |
| `L1` | 可观测动作 / 工具调用记录 / 明确执行痕迹 | 全权 |
| `L2` | 复盘模型判定当日确实执行了该流程 | 半权 |
| `L3` | 仅文本共现（"忘了跑 memory_stats"这类提到） | 0 分，只记一行事件 |

**两个阈值**：低于 `0.5` 会被检索标注「先验证再用」，高于 `0.85` 视为事实、不再主动提示复核。

**证伪不删条目**：

```
memory_verify(item_id="x_xxx", ok=false)
```

按同一条幂律扣分、封底 0，**行留着**。经验的价值在于「它曾经是个结论」，被推翻本身是知识；
删掉之后三个月后回头只会看到"这条从没存在过"，而不是"这条错了"。

**经历没有可信度。** 对经历调 `memory_verify` 会直接报错——它只是发生过的事，
真假由事实决定，它的"可信度"是遗忘等级的派生值。

## 经验过时了怎么办

**不要**改旧条目（改不了，触发器会拒绝），**不要**删。两条路：

```
# 有替代结论 → 新写一条，让旧的失效
memory_write(kind="experience", content="项目改用 UI Toolkit", invalidates="x_旧的id")

# 暂无替代，只是知道它不对了 → 只置失效
memory_invalidate(item_id="x_旧的id")
```

旧条目 `invalid_at` 非空，默认检索不再返回，但 `memory_search(include_invalid=true)` 能查到历史。
这条链是**单向的**，已失效的条目不能被"复活"——写错了就再追加一条新的。

对自己写错的经验放宽心：扣分、标失效、重写一条，都比"将就着用一条半对的结论"好。

## 写经验前会自动查重

`memory_write(kind="experience")` 会在库里先比一遍向量。**和既有条目太像就不会新建**：

```json
{"ok": true, "deduped": true,
 "item": {"id": "x_abc", "content": "..."},
 "note": "与 x_abc 高度重复，未新建；已给该条加活跃度、原样返回。"}
```

看到 `deduped: true` 说明**你的知识已经在库里了**，这不是失败，别重试、别换个说法再写一遍。

- 内容确实更准确/更新 → 带 `invalidates` 重写：`memory_write(kind="experience", content="新的", invalidates="x_abc")`
- 确实是另一条结论（只是措辞像）→ `memory_write(kind="experience", content="...", allow_duplicate=true)`

两类情况不要搞混：**同一个结论不要存两份**，两份各自"正确"，以后没有任何机制会让其中一份被淘汰。
经历不查重——同一天做两次同样的排查，是两件事。

## 遗忘等级：决定还能不能被翻出来

每条记忆有个 `forget_level`（0~5）。它不是"重要性评分"，而是**检索权重的倍率**：
等级越高越容易被翻出来，0 级等于沉到遗忘层，常规检索扫不到，只有深度回忆才会碰。

**初始等级由 `importance` 决定，不能直接设顶档：**

| importance | 初始等级 |
| --- | --- |
| ≥ 0.55 | 4 |
| 0.30~0.55 | 3 |
| < 0.30 | 2 |

顶档（5）只能靠活跃度挣——录入即顶档等于让每条新记忆都来抢席位。

**升降由周期末的活跃度裁定**，活跃度是「周期内每次被检索到的相关性平方累加」。
相关性低于 0.35 的命中不计分：查到了但明显不相关，不该给记忆续命。

每个周期**最多动一级**，且有滞回双阈值（升要过 `up_threshold`、降要过 `down_threshold`）——
防抖，避免在边界上反复横跳。经历的周期比经验短（同一等级下 30 天 vs 90 天），
因为经历本来就老得快。

**裁定要有人跑**：`memory_judge` 把「该升降了」的一次处理完。

```
memory_judge()                 # 跑到期裁定（只有项目库了）
memory_judge(dry_run=true)     # 只看判定结果
```

它是**纯机器计算**，不调模型、不动正文，只改 `forget_level` / `activity` / `period_start`。
没到期就一个字节都不写，所以定时任务里天天跑没有代价。**维持原级也要回写**——
不清零活跃度它就会永远停在「已到期」，每轮重算同一个结论。

别指望它替你压缩或删除：压缩是生成任务（`memory_compress_*`），删除只出候选。

**压缩跟着等级走**：等级降下来，经历就被压短一档。
判据只有一条 —— `compression_level < required[forget_level]`，这张表在 `[compress]` 里。
经验**永不压缩**：压缩会丢精确性，而经验的全部价值就在精确性。

### 遗忘层还能捞回来

0 级条目正文完整，只是不在常规检索里。想找它得显式捞：

```
memory_deep_recall("那次彻底失联的排查")     # 只翻 0 级，命中带「已遗忘」标记
```

**经历会被捞活**：每次命中记一次 `revive_hits`，攒够 2 次就复活到 **1 级**（不是 3 级）——
想起一次不代表记住了，回 3 级等于给一次免费续命。`memory_recall` 在常规捞不到东西时
会自动兜一层深度回忆，所以日常不用特意调。

**经验不会被捞活**：`revive_hits` 只有经历表有。经验落进 0 级只能人工恢复或等清理。

0 级待满 `level0_purge_days`（180 天）还没攒够复活次数，就进删除候选 —— 只报告，删不删你说。

## 检索：别只查一次

```
memory_search("引导 不触发", kinds=["experience"], limit=6)   # 只查经验
memory_recall("当前在做的事")                                  # 按话题召回 + 给命中项记活跃度
```

**`memory_search` 只查不改**（除访问计数），`memory_recall` 会强化命中项——日常用 recall，
单纯核对用 search。**两者都不看遗忘层**，要翻旧账用 `memory_deep_recall`。

**要查历史别忘开两个开关**：`include_archived=true`（归档区）、`include_invalid=true`（已失效）。
默认都关着，因为大部分时候你不想要三年前的噪音；但排查"这条为什么变了"的时候，
失效链就是唯一线索。

`memory_stats` 先看库健不健康：各表条数、待归档数量、待补向量的条数。

## 工具速查

| 工具 | 用途 |
| --- | --- |
| `log_append` | 追加当天日志。白天的主力工具 |
| `memory_write` | **唯一写入口**，`kind` 必填：`experience` / `episode`。经验会先查重，`deduped=true` 表示未新建 |
| `memory_verify` | 给经验落一条证据。`ok=true` 加分、`ok=false` 扣分（都不删行） |
| `memory_invalidate` | 让经验失效（过时但暂无替代）；对经历会拒绝 |
| `memory_promote` | **已下线**：全局库关闭，调用会明确报错 |
| `memory_list` | 列条目；`kinds` 不传即全部 |
| `log_list` | 按日期列日志 |
| `memory_recall` | 按当前话题召回 + 强化命中项 |
| `memory_search` | 只查不改；`format="full"` 取全文 |
| `memory_deep_recall` | 只翻遗忘层（0 级）；命中的经历累计复活次数 |
| `memory_judge` | 跑到期裁定：按周期活跃度升降等级；没到期什么都不写 |
| `consolidate_preview` | 取当天待复盘日志 |
| `consolidate_apply` | 提交复盘结果（`experience=[...]` / `episodes=[...]`） |
| `rules_get` / `rules_append` | 读/追加信条 |
| `memory_stats` | 统计与健康提示（按表分列） |
| `memory_use_workspace` | 切换到另一个项目的工作区（一条配置服务多项目） |
| `memory_archive` | 归档低价值记忆（默认只预览，按表各自 TTL） |
| `memory_unarchive` | 从归档恢复 |
| `memory_purge_candidates` | 列删除候选（只报告） |
| `memory_purge` | 物理删除，需 `confirm=true`，只能删已归档的 |
| `memory_compress_preview` | 取待压缩队列（按遗忘等级推出「压得不够深」的经历，只读） |
| `memory_compress_apply` | **定向覆盖**原经历（改 `content` 与压缩级别，`id`/`at` 不变） |
| `memory_maintenance` | 补 embedding |

**已下线的工具别再调**：`memory_review` / `memory_review_list`（复核梯子随 `state` 一起删除）、
`memory_recompress_preview` / `memory_recompress_apply`（按年龄判压缩，已被等级驱动取代）、
`fact_write`。`memory_write` 也没有 `verifies` 参数了——「我看了，还成立」要表达就走 `memory_verify`。

## 一条 server 配置服务多个项目

```
memory_use_workspace(path="D:/proj/YourProject")
```

切换后所有读写都落在该项目自己的 `.ai_memory/workspace.db`，**项目之间仍然物理隔离**。
`persist=true`（默认）会记住这次选择，下次 server 启动自动接上。

**什么时候要调**：会话开始 `memory_stats` 显示的工作区不对；用户提到了另一个项目的记忆。

**工作区来自哪里**（优先级从高到低）：

1. `--token` 令牌文件
2. `--workspace` 命令行
3. `HM_WORKSPACE` 环境变量
4. cwd 向上查找**已存在**的 `.ai_memory`
5. cwd 处在一个像项目的目录里（有 `.git` / `ProjectSettings` / `package.json` 等）
   → **在项目根自动建立**，不用手动 init
6. 上次用过的工作区（`~/.humanity-memory/last-workspace.txt`）
7. 无 → 报错（全局库已关闭，没有兜底库）

在子目录（如 `<项目>/Assets/Scripts`）里启动时，会自动归位到项目根，不会在子目录建库。
用户主目录和盘符根永远不建。

## 存储布局

```
<项目>/.ai_memory/workspace.db    # 项目记忆（物理隔离）
<项目>/.ai_memory/CORE_RULES.md   # 项目信条
~/.humanity-memory/CORE_RULES.md  # 全局信条（仍然生效，静态注入）
```

**项目之间物理隔离**，换个项目就看不到上一项目的记忆。没有例外了。

**全局库已在 2026-11-17 关闭**（原 `global.db` 改名为 `global.db.retired-20261117`）：
AI 自动写入的跨项目库会污染所有项目——在 A 项目看到一条"结论"，实际可能是 B 项目里
AI 臆断的。所以：

- `scope="global"` 写入会报错，`memory_promote` 已下线
- 真正该跨项目共享的**硬约束**写进 `CORE_RULES.md`（`rules_append(scope="global")` 仍可用，
  那是信条不是向量库）
- 剩下那些"跨项目但不硬"的内容，绝大多数其实只属于某一个项目，留在项目库更准确

## 复盘

日志是原始素材，需要定期压成经验和经历。**这不是你的模型之外的事**——
复盘由当前会话的模型执行，你不用调用外部 LLM：

1. `consolidate_preview(day="today")` 拿到当天日志（**不返回存量经验**）
2. 你自己阅读、提炼：哪几条够格当经验、当天怎么压成一段经历
3. `consolidate_apply(experience=[...], episodes=[...], purge=true)` 提交
4. 原始日志被清空，经验和经历留存
5. `memory_judge()` 收尾：跑到期裁定（纯机器，没到期不写任何东西）

**你只做三件事：写条目、给初值、报证据。** 不判断该升到几级、不算分值、
不逐条比对存量找重复——查重在写入时由工具做。要做的事和不要做的事，模板里列全了。

```python
consolidate_apply(
    experience=[
        # 可复用的结论。confidence 是起点：易变 0.3 / 一般 0.5~0.6 / 机制 0.8
        {"content": "Unity 2022.3 里 Prefab 的 m_LocalRotation 手改会静默失效",
         "confidence": 0.8, "source": "今天实测 Unity 日志 + 结果对比"},
    ],
    episodes=[
        # 当天发生了什么。importance 决定初始详细程度
        {"content": "修 #11809 三方登录 20s 静默锁：先怀疑网络层，最后定位到 OnThirdLoginFail 被门控",
         "importance": 0.9},
        {"content": "顺手改了个 typo", "importance": 0.2},
    ],
    summary="一天一句话，只进 digest 留档",
)
```

**`summary` 不会变成一条记忆**——它只写进当天的 digest。总结和「发生过的事」是两类东西，
混在一起会把复盘自己写的话当成经历留进库里。

**提交后核对 `created_experience` / `created_episodes` 条数是否与请求一致**，不要只看 `ok=true`。

详见 `references/consolidate-guide.md`。

**配成定时任务**：每个工作区各建一个，只复盘自己那个库。直接抄
`references/consolidate-task.md` 的模板，把两处 `{{占位}}` 换成这个项目的情况即可，
别把一个任务写成跨项目扫描。

### 接入一个新工作区（三步，固定顺序）

用户说「给 X 项目初始化记忆系统」时按这三步走完，细节与检查清单见
`references/workspace-onboarding.md`：

1. **初始化记忆库** —— 先探查 git 根与已有 `.ai_memory`；**已存在就核验、不删重来**
   （除非用户明确说「删了先」）。`init` 是幂等的，跑完用 `doctor` 和子目录 `stats` 验证。
2. **编写定时复盘任务** —— **先向用户确认配置再创建**：循环周期、执行时刻、
   **持续时间**（`validUntil`，不设即无限期）、工作目录 `cwds`。别把「凌晨」这类模糊词
   自己拍成某个时间点，也别默认无限期；prompt 必须显式切库并校验 `workspace_db`。
3. **把原本的记忆文档以日志录入，等待复盘** —— 只读盘点旧来源，
   **按大条目（`##` 章节 / 独立事项）拆成多条日志，防止单条过大**；原文保留、不预先提炼，
   用 `store.append_log(at=...)` 保留原始日期（`log add --day` 对 add 无效）。
   只验证 `consolidate_preview` 能捞到，**不要手动复盘**，留给定时任务。

## 经历：起点由 importance 决定，之后随遗忘等级变短

仿生记忆是**两个维度**，只做一个都不对。

### 维度一：重要性决定一开始写多细

| importance | 初始级别 | 写多细 |
| --- | --- | --- |
| **≥ 0.75** | level 0 | 完整叙述：背景、当时的判断、试错过程、精确报错、最终结论 |
| **0.45~0.75** | level 1 | 要点：关键步骤 + 结论，不铺陈过程 |
| **< 0.45** | level 2 | 一句话说清是什么 |

**琐事不该有 level 0。**「昨天吃了什么」生下来就该是一句话——
先写成完整叙述再等它压缩，等于给琐事录纪录片。

**典型高重要性**：被用户明确批评、重大失误、关键架构决策、排查很久的疑难、
有情绪张力的对话。这些要保留原始措辞，几年后回看才有价值。

### 维度二：等级让它变短

| 落到等级 | 目标压缩级别 | 内容变成 |
| --- | --- | --- |
| 5 / 4 / 3 | 0 | 完整，不动 |
| 2 | 1 | 去冗余，保留关键步骤 |
| 1 | 2 | 只留结论与根因 |
| 0 | 3 | 标题级 + 一句摘要 |

压缩走队列，**没有「待压缩」标记**：压完把 `compression_level` 写到目标值，自然出队。

```
memory_compress_preview()        # 队列为空就整步跳过，不用管
memory_compress_apply(items=[{"id": "e_x", "content": "更短的版本"}])
```

三条硬规矩：
- **定向覆盖，不是新建**。同一件事在库里只能有一份，新建压缩版会让 `at` 漂成压缩时刻
- **不要合并条目**。同一天两件事被写成两条是录入阶段的问题，压缩阶段拿不可逆的覆盖去补救
- **`level` 可省略**（缺省写目标值）；给的话必须落在 `(当前, 目标]`，且新内容不能比原文长

## 记忆会淡忘，但不会被悄悄删掉

| 表 | 归档条件 | 会压缩吗 |
| --- | --- | --- |
| 经验（`knowledge`） | 3 年没被碰过、且访问 ≤ 1 次 | 不压缩（压缩会丢失精确性） |
| 经历（`episodes`） | 1 年没被碰过、且访问 ≤ 1 次 | ✅ 随遗忘等级压缩 |
| 日志（`logs`） | 复盘后清空（按复盘，不按访问） | 已有 |

**归档 ≠ 删除**。归档只是让它在默认检索里消失，正文一个字都没动，`include_archived=true` 随时能查回来。

物理删除必须显式调用 `memory_purge(ids, confirm=true)`，而且**只能删已归档的**——没归档的会被拒绝，这是有意的保护。
落进 0 级遗忘层满 180 天、或归档满 180 天的，才会出现在删除候选里。

```
memory_archive(dry_run=true)        # 先看会动哪些（按表分组报）
memory_archive(dry_run=false)       # 确认后执行
memory_purge_candidates()           # 定期看删除候选（只报告，不删）
```

要删的时候先问用户，说清楚「这些已经归档 N 天、从未再被访问」。**不要自己决定删**。
