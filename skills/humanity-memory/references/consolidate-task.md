# 定时复盘任务提示词模板

一个工作区配一条自动化。**一条任务只复盘一个库** —— 跨项目扫描会把别的项目的记忆
写进当前库，事后很难理清。

复制下面整块，把 `{{...}}` 换成这个项目的实际情况，其余不要改。

## 模板

```
对当前工作区执行一次记忆复盘。你只做三件事：写条目、给初值、报证据。
分值、等级、遗忘、查重都由工具算，不要替它们做判断。

1. 确认工作区
   memory_stats —— 看 working_dir 是不是你预期的项目。不对就停下说明，不要继续。

2. 取素材
   consolidate_preview(day="today")
   不传 day 也行，它会自动补最近一个还有积压的日期。
   你只需要读返回的 logs。不要读存量经验去逐条比对 —— 查重在写入时由工具做。

3. 写条目（第一件事）
   episodes：当天发生了什么。一条一个单一事务。
   experience：换掉单号 / 任务 ID / 资源名之后仍然成立的机制与约定。
   {{这个项目里哪些结论够格进 experience、哪些只能进 episodes}}

4. 给初值（第二件事）
   importance 0~1：决定初始遗忘等级，也决定一开始写多细。
   confidence 0~1（仅 experience）：初次写下时你有多确信。易变的 0.3、
   一般结论 0.5~0.6、机制性结论 0.8。它是起点，之后由证据调整。
   {{这个项目的默认值，例如「负责人拍定的基调给 0.9」}}

5. 报证据（第三件事）
   只有本次复盘真的拿到了可验证的东西（跑过命令、看到报错、用户明确确认）才报，
   写完条目后调 memory_verify(item_id, ok=true, level="L1", reason="...")。
   L1 可观测动作 / L2 复盘判定 / L3 听说（恒 0 分）。
   拿不出来就不报。宁可留 0.3，不要凑。

6. 提交
   consolidate_apply(experience=[...], episodes=[...], purge=true)
   提交后核对 created_experience / created_episodes 是否与请求一致，别只看 ok=true。
   如果这次明确推翻了某条旧结论，在那一项的 experience 里带 invalidates=旧id；
   不知道有没有重复就交给查重，不要把存量经验全读一遍去找冲突。

7. 收尾（纯机器动作，不产生判断）
   memory_judge()                # 跑到期裁定；没到期返回空，不写任何东西
   memory_compress_preview()     # 队列为空就跳过整步

8. 回报一句话
   写了几条 experience / episodes、清掉多少日志、warnings 有没有内容。不要复述正文。

不要做的事：
- 不要判断「这条该升到几级」「这条还成不成立」「该不该遗忘」—— 工具按活跃度裁定
- 不要给分值，只给 bool 和证据级别
- 不要读存量经验做冲突比对；要取代就在第 6 步给 invalidates
- 不要把 logs 原文复制进 episodes，那不是压缩，是搬家
- 没有素材就提交空数组，不要硬造

纪律：
宁可少写。一天 0~3 条 experience 是正常的，10 条说明标准太松。
带单号的排查结论只能进 episodes。
日志原文保留的是精确性（报错栈、时间线、当时的措辞），别在复盘时把它抹平。
```

## 占位符怎么填

| 占位符 | 填什么 | 例子 |
| --- | --- | --- |
| `{{这个项目里哪些结论够格进 experience}}` | 一条能照着判断的标准，不是分类法 | 「机制、约束、接口约定够格；带 bug 号的排查过程只进 episodes」「指不出代码落点的先别写」 |
| `{{这个项目的默认值}}` | 只写这个项目特有的初值约定 | 「负责人拍板的规范给 0.9」「资源命名约定给 0.7」 |

**只填这两处。** 别把整篇都改成项目定制 —— 通用规则是这套模板的价值所在，
每个项目改一遍就会漂成七八个版本，最后没人知道哪份是对的。

## 为什么这么写

**为什么第 3 步不让读存量经验**：旧版本要求模型拿 `existing_experience` 全量比对找冲突，
本质是把「逐条核对」搬进了复盘。查重现在由写入路径的向量 top-k 做（`dup_floor` 0.90），
模型再比对一遍只会产生两个后果：token 暴涨，以及凭措辞猜"像不像"。

代价是模型可能漏掉真正该取代的旧结论。这个代价是可接受的 ——
**漏掉的后果是一条重复条目（下次写入会被查重拦下），错判的后果是一条好结论被误失效。**
后者不可逆，前者只是噪音。

**为什么先 `memory_stats`**：一条 MCP 配置服务多个项目，工作区由 cwd / 上次选择决定。
复盘多半在无人值守时跑，工作区错了等于往另一个库灌垃圾。

**为什么强调 `purge=true`**：日志不清空，下次 preview 还捞同一批，同一段内容被反复提炼。
要留原始凭证才改 `purge=false`，它只标 `consolidated=1`，不会再进 preview。

**为什么冲突走 `invalidates` 而不是删旧的**：经验是可累积的。「以前的结论」和「现在的结论」
同时存在、加上失效链，才是完整答案 —— 三个月后有人问"为什么当初那么做"，失效那条是唯一线索。

**为什么不让模型打分**：模型可以用措辞影响自己给的分数（"这条非常重要"→0.95）。
只让它回一个 bool 加一个证据级别，分值由公式算，杜绝这种漂移。
代价是分值的形成过程离开了上下文，所以工具侧必须留审计（`memory_events`）。

**为什么第 7 步有 `memory_judge`**：它是纯机器计算，不碰正文、没到期就不写，
放在复盘尾巴上等于"顺手把该升降的处理掉"，和 AI 的判断完全解耦。

## 跑完看什么

- `memory_stats` 里 experience 一天涨 10 条以上 → 标准太松，收紧上一条纪律
- `consolidate_apply` 的 `warnings` 有内容 → 多半是重复条目被查重跳过，看一眼
- `skipped_experience` 非空 → 写进去的条目与存量高度重复，下次少写点
