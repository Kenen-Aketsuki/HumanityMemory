# 复盘指南

## 为什么需要复盘

日志是原始素材：杂乱、带时间上下文、会随时间失去意义。
经验是提炼后的结论：简短、长期有效、可复用。带单号的一次性结论不算经验，写成经历。

中间这一步压缩，就是复盘。它同时做三件事：

1. **提炼** —— 从当天日志里抽出可复用的结论，把一次性事件写成经历
2. **压缩** —— 把当天的过程压成一段保留因果的经历
3. **清理** —— 清空原始日志，防止噪音堆积

## 谁来做

**当前会话的模型。** 不需要额外配 LLM——这是刻意的设计：
用一个独立的小模型做总结，质量通常不如你正在用的模型，而且要额外维护 key 和配置。

流程是两步：

```
consolidate_preview(day="today")   → 你拿到原始日志
   ↓（你自己读、想、提炼）
consolidate_apply(experience=[...], episodes=[...], purge=true)  → 提交
```

## preview 返回什么

```json
{
  "day": "2026-11-03",
  "log_count": 12,
  "logs": [{"id": "l_xxx", "at_iso": "...", "content": "...", "tags": []}],
  "instructions": "..."
}
```

**不再返回存量经验。** 早先这里会给一份 `existing_experience`，要求模型逐条比对避免重复——
那等于把「逐条核对」搬回复盘，token 暴涨且只能凭措辞猜"像不像"。
查重改由写入路径的向量 top-k 做（`dup_floor` 0.90），命中就转强化、不新建。
只有你**明确知道**某条旧结论被这次发现推翻时，才在写入时带 `invalidates`。

## 提炼经验的判断标准

从日志里挑，只有满足全部三条的才提成 `kind="experience"`：

1. 明天、下个月、明年都还成立
2. 一句话能说清，不需要"那天"这个上下文（换掉单号/任务 ID 仍成立）
3. 是结论，不是过程

```
日志："排查布局错乱，试了 ScaleWithScreenSize 无效，最后发现 anchor 被写死"
✅ 提取："预制体里的 RectTransform anchor 会被写死，改布局先检查它"
❌ 不提取："今天排查了布局错乱"        // 过程，不是结论
❌ 不提取："试了 ScaleWithScreenSize"   // 中间尝试，已被排除
```

**一般是 0~3 条。** 如果一天能提炼出 10 条"经验"，说明你的标准太松了——
那些八成还是日志级别的内容。

### confidence 给多少

这是复盘时唯一需要你判断的数值，别随便填：

| 值 | 判据 |
| --- | --- |
| **0.8** | 有代码落点、今天实测过、可复现 |
| **0.5~0.6** | 观察到了，但只在一个场景下确认过 |
| **0.3** | 易变：版本号、路径、外部依赖行为、别人的口头承诺 |

**给高了比给低了危险得多**。超过 `treat_as_fact`(0.85) 就视为事实、不再提示复核；
一条不该被信任的结论标到那个位置，它会被反复当成结论推荐，而没有人会去验它。

带单号的排查结论不是经验，但它值得留：写成 `kind="episode"`，
一句话「现象 → 根因 → 落点」，一个问题一条。别为了省事把它塞进 experience。

## 写经历

把当天的事写成 1~3 条经历，一条一个单一事务，保留**因果链**：

```
✅ "重构记忆库的存储层。先踩到 mcp 2.3 的 API 改名（FastMCP→MCPServer），
    又遇到 doctor 双连接死锁（DDL 未释放写锁）。最终确定双库三层结构，
    用触发器把 append-only 变成数据库层硬约束而不是应用层自觉。"
```

保留"先踩了什么坑、为什么这么定"——这是以后回看时最有价值的部分。
不要写成流水账（"上午做了 A，下午做了 B"），那和原始日志没区别。

**importance 决定它一开始写多细**：≥0.75 完整叙述、0.45~0.75 要点、<0.45 一句话。
琐事直接给 0.2，别让它以完整叙述的形态进库。

如果当天没什么值得留的，`episodes` 传空数组也可以。**不要硬编**。

**`summary` 不会变成一条经历。** 它只写进当天的 `digests` 留档。
「总结」和「发生过的事」是两类东西，混在一起会让复盘自己写的话冒充成经历。

## 冲突处理

提炼出新结论，而旧条目与之矛盾时：

```json
{
  "content": "项目改用 UI Toolkit 做 UI",
  "invalidates": "x_旧条目的id"
}
```

旧的自动失效，指向新的。**不要**手工去删旧条目——历史是有价值的，
"曾经用 UGUI"这个信息在排查老问题时可能有用。

## purge 的取舍

- `purge=true`（默认）：原始日志物理清空。省空间、防噪音。
- `purge=false`：保留原始日志，只标记 `consolidated=1`。

什么时候用 `false`：复盘质量没把握，想先留着原始素材核对；
或者这一天有重要的原始记录（完整报错栈、精确时间线）值得留档。

注意：即使 `purge=false`，日志也已经被标记为已复盘，不会再出现在下次 preview 里。

## 节奏

- **每天一次**，在当天结束或第二天开始时
- 用自动化（定时任务）触发时，prompt 里写清楚：先 preview、再总结、再 apply
- 连着几天没复盘时，可以逐天补：`consolidate_preview(day="2026-11-01")`

## 什么不该做

- 不要把日志原文直接塞进 `episodes`（那是复制，不是压缩）
- 不要为了"显得有产出"而硬造经验
- 不要跳过 preview 直接 apply——你没有素材就没法总结
- 不要顺手调 `memory_verify`：复盘拿到的是日志文本，撑不起 L1/L2 证据
- 不要在 purge=true 之后后悔：原始日志删了就没了（`digests` 表里只留了 id 和统计）
