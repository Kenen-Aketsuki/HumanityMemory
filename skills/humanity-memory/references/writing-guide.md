# 写入指南

## 核心原则：默认写日志

白天对话里的绝大多数内容都应该写成**日志**，而不是经验。

原因：当下你觉得"这很重要"的东西，八成带着当天的临时上下文。
如果直接写成"永久结论"，三个月后它会变成无法理解的碎片。
日志先兜住原始素材，复盘时再提炼——这才是人类记忆的工作方式。

## 什么时候必须直接写经验

只有同时满足这三条才直接写 `kind="experience"`：

1. **三个月后仍然成立** —— 不会因为版本升级、方案调整而改变
2. **一句话说得清** —— 不依赖当天上下文就能理解，换掉单号/任务 ID 仍成立
3. **是可执行的结论** —— 不是过程描述

只满足 1、3 但要随版本变 → 还是写经验，但 `confidence` 压到 0.3~0.4。
**不要因为"它可能会变"就不写**——易变性靠可信度表达，不靠另立一类。
之后它被 `memory_verify` 反复确认就自然爬上来，被证伪就掉下去。

三条都不满足、但那件事以后要能查回来 → `kind="episode"`，写清楚时间与因果。

```
✅ "这个项目的 UI 层用 UGUI，不用 UI Toolkit"
✅ "提交前必须跑离线编译自检"
✅ "主人偏好中文输出，用表格承载结构化信息"
❌ "今天决定用 UGUI"            // 时间性太强，是日志
❌ "Bug #10805 根因是 StockBread 三条静默出口"  // 绑单号 → episode，不是经验
❌ "排查后发现改用 UGUI 更好"    // 有过程，是日志
```

## 经验的正确写法

**一条 = 一个可独立成立的陈述。** 不要在一句话里塞多个结论。

```
✅ "设施存档用总文件存共有信息、模块分文件存细节"
✅ "设施实体通过唯一 ID 关联模块存档与配置"
❌ "设施存档用总文件和分模块结构，实体靠唯一 ID 关联，逻辑类用全名绑定"
   // 三个结论塞一起，检索时命中一条带出三条无关内容
```

带上**理由**会让经验更有价值，但要控制长度：

```
✅ "选 logic class 全名绑定而非枚举工厂：配置是手写 XML，加枚举要改代码"
```

这条 45 字，把决策和理由都装进去了。经验上限 500 字，但**越短越好**，
超过 100 字通常说明它该拆成两条，或者根本该是日志。

## 重复的不会写进去，只会给旧条目加分

写经验时工具会先在库里比一遍向量，太像就不新建，直接返回既有条目并带上
`deduped: true`。所以：

- **不要为了防止重复而先搜一遍**——查重已经做了，你搜那一次只是多花 token
- **看到 `deduped: true` 就收手**，别换个说法再写一次，那还是同一条
- 内容确实更新了 → 带 `invalidates` 重写（旧的置失效、新的顶上）
- 是另一条独立结论、只是措辞像 → `allow_duplicate: true`

写重了没有机制会替你收拾：两条各自"正确"，压缩阶段也没有理由丢哪一条。

## confidence 怎么给

`confidence` 是**起点**，不是评价。之后一律由 `memory_verify` 按证据调整。

| 值 | 什么内容 |
| --- | --- |
| **0.8** | 机制性结论：有代码落点、我刚验证过、可复现 |
| **0.5~0.6** | 一般结论：观察到了，但只在一种场景下确认过 |
| **0.3** | 易变事实：版本号、路径、资源配置、外部依赖行为 |

给低分不丢人。**给高分的代价更大**——一条不该被信任的结论标 0.8，
它会在每次检索时被当成事实推荐，而没有人会去验它（`treat_as_fact` 阈值以上不再提示复核）。

## 经历的写法

经历可以长、可以有过程、可以有情绪。它是原始素材，不是最终结论。

```
✅ "排查布局错乱，先怀疑 Canvas 缩放模式，试了 ScaleWithScreenSize 无效，
    最后发现是 RectTransform 的 anchor 在预制体里被写死了。改完正常。"
```

写清楚**试过什么、排除了什么**——这些在复盘时是提炼经验的关键信息，
而且以后遇到类似问题能直接复用排查路径。

**一条经历 = 一个单一事务。** 别把一天的十件事写成一条；也别把一件事拆成十条。
判断标准：如果它需要一个"标题"才能概括，那就说明它其实是多条。

## 日志的正确写法

日志是白天的**流水账**，允许零散、允许重复、允许没结论。

```
✅ "先试了 A，报 CS0246；改成 B，编译过但运行时 NRE；怀疑是 Pool 里没 Reset，
    明天继续。"
```

它不求可读，求**原始**。精确的报错栈、完整时间线、当时的措辞，
只有日志里才有——复盘一压就没了。所以重要的东西白天就 `log_append` 进去，别等。

**日志不参与等级机制**（没有 `forget_level`），也不做压缩调优，它的用途是"当天回头看一眼"和"复盘素材"。
真正要长期留的东西，复盘时提炼成经验或经历。

## importance 怎么标

importance 决定**初始遗忘等级**，也就是它多容易被检索到。

| 值 | 含义 | 默认来源 |
| --- | --- | --- |
| 0.9~1.0 | 硬约束，违反就出事 | 手动提 |
| 0.7~0.8 | 重要约定/选型 | 经验默认 0.8 |
| 0.3~0.4 | 一般记录 | 经历默认 0.4、日志默认 0.3 |

importance 只占检索分数的 12%，**别指望靠调它补救糟糕的写法**。写清楚 > 调权重。

## 只有项目库了

**全局库已在 2026-11-17 关闭**（§8.2），`scope="global"` 写入会直接报错。
写之前先问：**换个项目还需要它吗？**

- 需要且是硬约束 → 写进 `CORE_RULES.md`（`rules_append(scope="global")`）
- 需要但只是习惯 → 每个项目各写一条，别指望跨项目同步
- 不需要 → 留在项目库

为什么连"跨项目经验"也砍了：全局库是公有空间、没人审核，AI 一次臆断会污染所有项目，
且跨项目污染比单项目难排查得多——你在 A 项目看到的一条"结论"，可能来自 B 项目的幻觉。

## tags

2~5 个，用于**过滤**不是检索。选以后真会用来筛的词：模块名、技术栈、问题类别。

```
✅ ["Unity", "存档", "重构"]
❌ ["重要", "记录"]      // 没有区分度
```

## 不要写的

- 临时文件路径、调试端口号
- "刚才那个命令失败了"（除非根因有复用价值）
- 从代码里 grep 一下就有的信息
- 用户的隐私细节——库是本地的，但也不必什么都记
- 一次性的执行细节（这些写日志也别写，复盘时会被过滤掉）
