# 写入指南

## 核心原则：默认写日志

白天对话里的绝大多数内容都应该写成**日志**，而不是事实。

原因：当下你觉得"这很重要"的东西，八成带着当天的临时上下文。
如果直接写成"永久事实"，三个月后它会变成无法理解的碎片。
日志先兜住原始素材，复盘时再提炼——这才是人类记忆的工作方式。

## 什么时候必须写事实

只有同时满足这三条才直接写事实：

1. **三个月后仍然成立** —— 不会因为版本升级、方案调整而改变
2. **一句话说得清** —— 不依赖当天上下文就能理解
3. **是可执行的结论** —— 不是过程描述

```
✅ "这个项目的 UI 层用 UGUI，不用 UI Toolkit"
✅ "提交前必须跑离线编译自检"
✅ "主人偏好中文输出，用表格承载结构化信息"
❌ "今天决定用 UGUI"            // 时间性太强，是日志
❌ "排查后发现改用 UGUI 更好"    // 有过程，是日志
```

## 事实的正确写法

**一条事实 = 一个可独立成立的陈述。** 不要在一句话里塞多个结论。

```
✅ "设施存档用总文件存共有信息、模块分文件存细节"
✅ "设施实体通过唯一 ID 关联模块存档与配置"
❌ "设施存档用总文件和分模块结构，实体靠唯一 ID 关联，逻辑类用全名绑定"
   // 三个结论塞一起，检索时命中一条带出三条无关内容
```

带上**理由**会让事实更有价值，但要控制长度：

```
✅ "选 logic class 全名绑定而非枚举工厂：配置是手写 XML，加枚举要改代码"
```

这条 45 字，把决策和理由都装进去了。上限 500 字，但**越短越好**，
超过 100 字通常说明它该拆成两条，或者根本该是日志。

## 日志的正确写法

日志可以长、可以有过程、可以有情绪。它是原始素材，不是最终结论。

```
✅ "排查布局错乱，先怀疑 Canvas 缩放模式，试了 ScaleWithScreenSize 无效，
    最后发现是 RectTransform 的 anchor 在预制体里被写死了。改完正常。"
```

写清楚**试过什么、排除了什么**——这些在复盘时是提炼事实的关键信息，
而且以后遇到类似问题能直接复用排查路径。

## importance 怎么标

| 值 | 含义 | 默认来源 |
| --- | --- | --- |
| 0.9~1.0 | 硬约束，违反就出事 | 事实默认 0.8，重要的手动提到 0.9+ |
| 0.7~0.8 | 重要约定/选型 | 事实默认 |
| 0.3~0.4 | 一般记录 | 日志默认 0.3 |

importance 只占检索分数的 12%，**别指望靠调它补救糟糕的写法**。写清楚 > 调权重。

## 全局 vs 项目

写 `scope="global"` 前先问：**换个项目还需要它吗？**

- 需要 → 全局事实（但先考虑是不是该写进 `CORE_RULES.md`）
- 不需要 → 留在项目库

规则类（"禁止 X"、"必须 Y"）应该进信条，不是全局事实。
信条静态注入、100% 命中；全局事实要靠检索，可能漏。

## tags

2~5 个，用于**过滤**不是检索。选以后真会用来筛的词：模块名、技术栈、问题类别。

```
✅ ["Unity", "存档", "重构"]
❌ ["重要", "记录"]      // 没有区分度
```

## 不要写的

- 临时文件路径、调试端口号
- "刚才那个命令失败了"（除非根因有复用价值）
- 从代码里 grep 一下就有的事实
- 用户的隐私细节——库是本地的，但也不必什么都记
- 一次性的执行细节（这些写日志也别写，复盘时会被过滤掉）
