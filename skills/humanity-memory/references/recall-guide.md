# 召回指南

## 什么时候召回

**该召回**：
- 会话开始，用户提到此前做过的项目/模块
- 用户问"上次那个问题怎么解决的"
- 准备做决策，想确认有没有相关约定
- 用户说"按之前说的来"——此时必须召回，不能凭印象

**不该召回**：
- 当次对话刚说过的内容
- 纯代码问题（直接读文件更快更准）
- 每次对话都无脑召回一次"看有什么记忆"——会注入无关内容，稀释注意力

## query 怎么写

召回质量几乎完全取决于 query。**写具体情境，别写关键词。**

```
❌ "Unity"
❌ "记忆"
✅ "正在重构设施存档的模块划分，要确认之前定的绑定方式"
✅ "用户在问 ASMR 下载器视频预览不自动播放"
```

原因：向量检索靠语义相似度。孤零零的 "Unity" 会同时接近所有 Unity 相关记忆，
排序结果基本由 importance 和新鲜度决定，等于没查到点子上。

## 读返回结果

```json
{
  "count": 3,
  "lines": ["[f_abc] (项目事实) 设施存档用总文件…", "[e_def] (2026-11-03) 重构了…"],
  "results": [
    {"type": "fact", "id": "f_abc", "score": 0.87, "vector_similarity": 0.79,
     "lexical_score": 1.0, "db": "workspace"}
  ]
}
```

- **`lines`** 是给上下文用的紧凑格式，直接拼进去
- **`type`** 三种：`fact`（事实）/ `episode`（经历）/ `log`（日志）
  - 事实最可信，直接当结论用
  - 经历是压缩叙述，可信但要留意它是"当时的理解"
  - 日志是原始记录，注意它的时间
- **`db`**：`workspace` 是当前项目，`global` 是跨项目事实
- **`vector_similarity` / `lexical_score`** 看这条是怎么被找到的：
  - 两者都有 → 语义和字面都命中，最可信
  - 只有向量 → 语义相近但用词不同，留意是否跑偏
  - 只有关键词 → 字面命中，可能是同名词汇造成的误召回（中文短词尤甚）

分数参考：`> 0.75` 高度相关，`0.55~0.75` 需自行判断，`< 0.5` 基本是噪音。

## 结果不理想时

按顺序排查，别急着改权重：

1. **query 太短或太泛** → 改成具体情境，收益最大
2. **记忆在别的项目里** → 项目之间是物理隔离的，查不到就是没有。
   如果这条确实该跨项目，考虑用 `fact_promote` 提升为全局事实
3. **事实被取代了** → `include_invalid=true` 看历史
4. **日志已复盘清空** → 原始日志没了，但压缩后的 `episodes` 还在，查 `kinds=["episode"]`
5. **压根没记过** → `memory_stats` 看总数
6. **embedding 没生效** → 返回里的 `degraded` 字段会提示，跑 `memory_maintenance`

权重（`HM_W_RETRIEVAL` / `HM_W_IMPORTANCE` / `HM_W_STRENGTH`）是最后才动的旋钮。

## 强化机制

`memory_recall` 会强化命中项（`access_count + 1`），`memory_search` 不会。

- 要注入上下文 → `memory_recall`，常用记忆会越来越容易被召回
- 只是查证、不想影响排序 → `memory_search`

强化是"用进废退"的「进」：对数增长，20 次召回后饱和，不会无限放大。
「退」由时间衰减负责：事实半衰期 3650 天（几乎不忘）、经历 180 天、日志 14 天。

## 注入上下文时

- 只注入 `lines`，不要塞整段 `results`——后者带一堆打分字段，占 token 还干扰阅读
- 3~6 条足够，多了反而淹没当前对话
- 发现某条明显不相关直接忽略，不用特地告诉用户
